# 檢核取代用的新資料源

## 核心原則

**逐欄比對相符率是基本功，不是本 skill 的重點。** 未受指導的 agent 已經會做逐日缺漏、
`TRIM` 去噪、批次檔追查、排除法 —— 這些不用教。

本 skill 只處理三件實測會失手的事，**每一件都會讓你交出一個錯的建議**：

1. 把新源的**修正**當成 bug，叫對方改回錯的
2. 停在「請查」，沒往下鑽出資料裡看得到的成因
3. 用樣本推論下結論，母體沒驗

## 何時用

- 舊表換新表、ETL 改寫、倉庫搬家、外部 feed 換供應商
- 「新資料源可以直接換過去嗎」「兩邊數字對不起來」
- 兩個 dataset 要逐欄比對

**不適用**：單一資料源的品質檢核（沒有對照組，排除法用不上）。

## 一、差異不等於缺陷：逐項驗，不是抓到一個就算

**新源常常修好了舊源的錯。** 把修正報成 bug，對方照做就會把正確值改回錯的 ——
這是本 skill 防的最嚴重失手，實測中真的發生過（新源新增的分類值其實是舊源標錯的更正，
卻被建議「移除這個混入的值」）。

**規則：每一個「新源多出來的值」「新源改判的列」，都要回底層欄位驗一次，
不能抓到一個就以為抓完了。**

驗法是**回到不會說謊的欄位**：分類欄改判了，就去看它底下的數值／代碼欄位。

```sql
-- 新源多出一個分類值？先看這批列的底層欄位長什麼樣
SELECT n.new_category, n.engine_cc, n.fuel_code, COUNT(*)
FROM {N} n WHERE {Y} AND n.new_category = '<新出現的值>'
GROUP BY 1,2,3 ORDER BY 4 DESC
```

底層欄位支持新的分類 → 是修正，寫進「新源比舊源好的地方」，並註明**不要改**。
底層欄位支持舊的分類 → 才是 bug。

**這條規則會反過來咬你。** 實測中，同一批列被兩次判斷判成相反的結論 ——
一次讀成「新源修好舊源的錯」（錯的），一次讀成「新源的詞彙體系不一致」（對的）。
差別在於後者**去看了舊源對同類列的處理是否前後一致**：

```sql
-- 舊源對「底層欄位長這樣」的列，是不是一律標成同一類？
SELECT o.old_category, COUNT(*) FROM {O} o
WHERE {Y} AND o.underlying_col <= 50 AND o.fuel_code = 1
GROUP BY 1 ORDER BY 2 DESC
```

舊源對同類列**前後一致** → 舊源有規則，新源是改規則不是修錯。
舊源**自己就不一致**（同樣的底層值散在多個分類）→ 才是舊源的錯。

**判定需要外部知識（法規、業務定義、產品規格）時，不要自己裁定** ——
列成待回答問題並附上你查到的底層事實，讓懂業務的人判。
猜錯的方向會讓對方把正確的值改成錯的。

**輸出上要有一節「新源修好舊源的地方（不要改）」。** 沒有這一節，讀的人會把整份
當成缺陷清單全部照改。

### 但這一節會變成垃圾桶：覆蓋率上升不是憑據

**「這欄從 3% 變 6.5%」不構成改善。** 實測中，一個日期欄的覆蓋率翻倍被寫進「不要改」
兼「可對高層報告的效益」，實際上是**把還沒發生的事件也填了日期** ——
25,754 張還在「領牌／配車／交車核准」狀態的訂單都被填了交車日期，下游交車數灌水九成。

**覆蓋率上升時，一定要問：新填的那批列，該有值嗎？**
找一個能判定的欄位交叉 —— 生命週期狀態、適用範圍、前置事件：

```sql
-- 新填的那批列，在舊源的狀態欄底下長什麼樣？
SELECT o.status_col, COUNT(*),
       COUNT(n.new_filled_col) AS 新源有值,
       COUNT(o.old_col)        AS 舊源有值
FROM {J} WHERE {Y} GROUP BY 1 ORDER BY 2 DESC
```

新填的列集中在「事件尚未發生」的狀態 → **是缺陷不是改善**，而且通常還連著一個
F 類問題（判定用的狀態欄沒搬過來，下游想過濾也過濾不掉）。

**「不要改」的每一項都要有機制憑據，不能只有前後兩個數字。** 合格的憑據長這樣：
舊源被截斷成固定長度、舊源同一代碼對到多個名稱、舊源同欄混用兩種寫法 ——
**指得出舊源錯在哪**。指不出來的，降級寫成「覆蓋率變化，待確認」，
放進待回答問題，**不准寫進效益**。

## 二、「請查 X」不是診斷，是把問題丟回去

發現一批列異常（對不到主檔、欄位全空、落到未分類桶）時，**先看那批列的原始欄位長什麼樣**，
再決定要不要交出去問。

```sql
-- 那批壞掉的列，它們的來源欄位裝了什麼？
SELECT n.source_code_col, COUNT(*)
FROM {N} n WHERE {Y} AND n.derived_col IS NULL
GROUP BY 1 ORDER BY 2 DESC LIMIT 10
```

實測中，一批「對不到車型主檔」的列，原因就寫在代碼欄裡：那格裝的是車型**名稱**字串
（還帶全形引號與尾綴），不是代碼。看一眼就知道，卻被寫成「請查為何對不到」。

**判準**：交出去問之前，先問自己「資料裡看得到答案嗎」。
看得到就寫成診斷；真的看不到，才寫成待回答問題**並附上切分查法**。

## 三、樣本推論要升級成母體判定

從幾百列樣本看出模式（欄位錯置、正負號翻轉、欄名與內容對不上）之後，
**用全母體的計數驗證它**，不要交出一個帶著「其餘 89% 未確認」的結論。

一組本該互相定義的欄位（訂價／折扣／總額、應收／已收／未收、期初／進出／期末），
驗它們的**等式**：

```sql
SELECT COUNT(*),
  COUNT(*) FILTER (WHERE c = a - b),
  COUNT(*) FILTER (WHERE c = a + b),
  COUNT(*) FILTER (WHERE a = c + b),
  COUNT(*) FILTER (WHERE c - a = b)
FROM {N} n WHERE {Y}
  AND a IS NOT NULL AND b IS NOT NULL AND c IS NOT NULL
  AND b <> 0        -- 必須排除退化列，否則命中率虛高
```

**等式全部是 0，本身就是一個獨立的發現**：這幾欄不是同一個口徑下的組成部分，
代表**新源內部沒有任何欄位可以互相驗算**。就算你能拿舊源推導出缺的欄位，
舊源退場後那個推導也沒東西校驗 —— 這比「欄名叫錯」嚴重，要單獨列一項。

等式不成立時，再看差額的形狀：`COUNT(DISTINCT 差額)` 只有幾個 = 固定費率；
上百個 = 另一個口徑。

## 輸出：六類 + 歸屬

分類是為了讓對方能派工，不是為了好看。**每一項要填滿：代號｜問題｜影響量級（帶數字）｜
嚴重度｜歸屬｜說明。**

| 類 | 名稱 | 排在這個順序的理由 |
|---|---|---|
| A | 統計值不對 | 數量不對，底下所有比率都不能信 |
| B | 欄位存在但整欄空白 | 最容易修、影響最大 |
| C | 欄位有值但覆蓋不完整 | 形狀（缺哪幾個月）比比例重要 |
| D | 欄名沒改但口徑換了 | 最危險：看起來正常，照欄名用就算錯 |
| E | 值域與格式異常 | 量大好修，先清掉才看得清 D 類 |
| F | 欄位沒搬過來 | 最顯眼、通常最不嚴重，所以排最後 |

**歸屬只有五種，不要自創**：`ETL 修`／`修上游來源`／`需新增欄位`／`先回答 Qn`／`下游自救即可`。

另外兩節不可省：**「已確認沒問題的」**（讓排查範圍收斂，比多列三個問題更能加快進度）、
**「新源比舊源好的地方（不要改）」**（見第一節）。

要交 md 報告或 xlsx 排查清單時，
**REQUIRED SUB-SKILL**：使用 `analysis-xlsx-output-skill`（它的 `references/excel-report-layout.md`
有 xlsx 排版規則）。發給人排查的 xlsx 要留可填欄（處理狀態／負責人／預計完成／回覆），
否則那只是報告，不是排查清單。

## Common Mistakes

| 出錯 | 修法 |
|---|---|
| 把新源的修正報成缺陷 | 每個改判／新增值都回底層欄位驗，並開一節「不要改」 |
| 把覆蓋率上升當成改善寫進效益 | 先查新填的那批列該不該有值；指不出舊源錯在哪就降級成待確認 |
| 寫「請查為何 X」 | 先查那批列的原始欄位；看得到成因就寫成診斷 |
| 「其餘 89% 未確認」 | 用全母體計數驗證樣本推論 |
| 等式檢驗命中率很高 | 忘了排除扣項為 0 的退化列 |
| 抄對照表時左右欄寫反 | 對照表逐列從腳本輸出讀，不要手抄 |
| 文件數字與重跑結果對不上 | 所有數字由同一支腳本產出，下游從它的輸出讀 |

## 紅旗

- 報告裡沒有一節「這些不用查」
- 報告裡沒有一節「新源比舊源好，不要改」
- 「不要改」裡有項目的憑據只是「覆蓋率從 X% 變 Y%」
- 出現「請查為何…」而資料裡其實看得到答案
- 結論帶著「其餘 N% 未確認」就交出去
- 一組本該互相定義的欄位，沒驗過它們的等式
- 分類表裡出現「其他」這一類
