# 據點易主影響分析 skill

**回答一件事：整體市場、原經營方、接手方，三個視角分別因為這次異動變成什麼樣。**

主產物是一張三視角變化表，不是一個「成功／失敗」的標籤。

---

## ⚠️ 這包含真實營運數據——GitLab repo 必須設為 Private

**這不是「最好設私有」，是必須。** 判準文件與測試案例裡直接寫著可辨識的商業數據：

| 檔案 | 含什麼 |
|---|---|
| `tests/case-real-yongkang/expected.md` | 真實公司名（睿能、康寶動力）、門市名（永康中華、安平中華、台南新營…）、各店領牌量、**各店業務人數**、臺南市與永康區的 GOGORO 市占率 |
| `references/judgment-framework.md` | 同一批數字被引用為實測證據（接手方 188→544、人力 8→10、人均 +131%、保留店 309→560…） |
| `references/domain-motorcycle.md` | 內部資料源路徑、欄位結構、剔除規則、競品品牌的實際量體 |

從這些數字可以回推出：**特定加盟商的營運規模與人力配置、GOGORO 在特定縣市的競爭態勢、公司內部的通路布局變化**。

**推 GitLab 前確認**：

1. Visibility 設為 **Private**（不是 Internal，除非你確定全公司都可以看人力編制）
2. 不要 fork 到個人 namespace 下的公開專案
3. 不要開 Pages、不要把 repo 加進任何公開的 CI 範例

**若日後要對外（廠商、顧問、開源）**：上表三個檔案都要脫敏，不是只刪測試資料。注意判準文件的說服力有一半來自「這條規則擋過一次真實失敗」——建議保留數字但去識別（改成「某六都」「某加盟商」），規則的可信度大致還在。

## 安裝

把整個 `store-handover-impact/` 資料夾放到你專案的 `.claude/skills/` 底下：

```
你的專案/
└── .claude/
    └── skills/
        └── store-handover-impact/
            ├── SKILL.md
            ├── references/
            ├── scripts/
            └── tests/
```

放好就生效，不用註冊。想裝在所有專案共用，放 `~/.claude/skills/` 也可以。

## 怎麼觸發

**通常不用特別叫它。** 講清楚事件就會自動載入：

> 永康中華門市 2025 年底從直營轉給康寶動力，幫我評估這次易主對各方的影響。

也會在這些情況觸發：有人拿市占或領牌數宣稱某次易主成功／失敗、評估開關店或通路重整的前後影響。

要強制指定就打 `/store-handover-impact`。

## 第一次用：先準備資料

**必要**（缺了跑不動）：

| 資料 | 最小欄位 |
|---|---|
| 交易明細 | 地區、時間、品牌／競品、售出據點（含經營公司）、數量 |
| 事件時間軸 | 交接日、各據點的經營公司歷史 |

**強烈建議**（缺了 Q5 做不出來）：

| 資料 | 最小欄位 |
|---|---|
| 買方地理 | 買方行政區／郵遞區號 × 據點 × 期別 × 品牌 |
| 人力編制 | 各據點人數，前後兩期 |

> **沒有競品資料就沒有市占分母，三視角有兩格會直接判「無法判定」。** 這不是 skill 偷懶——絕對量成長 30% 在一個成長 50% 的市場裡是輸。準備資料時這項優先度最高。

**人力編制資料檔通常沒有，要另外問業務端**，而且要講清楚含不含店長、含不含兼職。

## 換產業要改哪裡

`references/domain-motorcycle.md` 是**唯一**跟機車業綁定的檔案——詞彙對照、資料源、欄位、解析陷阱、剔除規則全在裡面。

- **同樣做機車業領牌資料**：直接用，但**先確認欄位沒變**。那份檔案記載的資料曾經被重新匯出過（9 欄→8 欄、門市欄整個消失），欄位表會過期。
- **換別的產業**：照著它的結構寫一份新的 domain 檔，**不要改判準文件**。判準是通用的（銷售量／市占率／競品／據點），domain 檔才是產業耦合點。
- **沒有對應的 domain 檔**：先跟使用者確認資料合約，不要猜欄位語意。

`scripts/loader_template.py` 是資料載入骨架，CONFIG 用**欄位名**對應（不是位置），換資料源改 CONFIG 就好。它內建四個自我檢查，會擋掉幾個會靜默出錯的坑。

## 改動判準之前

`references/judgment-framework.md` 的每條規則都擋過一次實測失敗。**改它之前先看 `tests/README.md`。**

兩個硬性要求（實測教訓）：

1. **每案至少跑 2–3 個獨立 agent，看的是收斂而不是單份品質。** 一份報告自稱「無紅旗成立」不是可靠信號——曾有三份各自都這麼說，並排才看出分歧，而分歧指向真正的框架洞。
2. **有分歧就起 verifier 交叉驗證。**

改判準只需跑 4 個核心案例，其餘按改動範圍選（見 `tests/README.md` 的分層表）。

> `tests/case-real-yongkang/` 需要專案的 `data/`（業務資料，未進版控）。你那邊沒有那份資料就跑不了，**核心案例會少一個，而且少的正是唯一的真實案例**——請自行留意。

## 已知限制（用之前先知道）

| 限制 | 後果 |
|---|---|
| **模組 E（在地客源流向）的規則從未實際執行過** | 十個測試案例沒有一個有買方地理資料，Q5 永遠是「無法判定」。那套規則等同沒跑過的程式碼。**你如果有買方地理資料，會是第一個真正驗證它的人——請回報結果。** |
| **只有一個真實案例、一個產業** | 其餘九個是合成資料，**盲點是作者的盲點**。 |
| **模組 C（交接斷層）幾乎永遠無法驗證** | 需要交接時點前後的月度資料，多數情況缺。缺就是「無法驗證」，**不可宣稱「交接無斷層」**。 |
| `loader_template.py` 只在一份資料上驗證過 | 而那份資料後來被重新匯出過。 |

## 遇到問題

- **數字對不上**：先查資料版本（是不是被重新匯出過），不要急著改框架。
- **判定和你的直覺不符**：先讀 `judgment-framework.md` 的「合理化話術對照表」與「紅旗清單」，多數直覺分歧在那裡有解釋。真的是框架錯了，照 `tests/README.md` 的流程補一個案例再改。
