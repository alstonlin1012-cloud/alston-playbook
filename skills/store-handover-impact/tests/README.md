# 回歸測試

改動 `judgment-framework.md` 之後，跑這裡的案例確認**沒有弄壞既有行為**。

## 為什麼需要這個

實測教訓：**一個 agent 跑完自稱「無紅旗成立」，是不可靠的信號。** 曾經三份報告各自都自稱無紅旗，但三份擺在一起才看出彼此的判定分歧——而那些分歧指向真正的框架洞。

所以測試流程有兩個硬性要求：

1. **每個案例至少跑 2–3 個 agent**（獨立、同一份 prompt）。看的是**收斂**，不是單份品質。
2. **有分歧就起 verifier 交叉驗證**：獨立重算數字、裁決哪份對、判斷分歧是不是框架講不清楚造成的。

## 案例（分層）

**10 個案例全跑要 20–30 個 agent，太貴。** 依改動範圍選：

### 核心（改 `judgment-framework.md` 一律必跑）

這四個各自擋住框架最大的一次失敗，涵蓋三贏／非三贏／衰退市場／不可判定四種基本形態。

| 目錄 | 分支 | 資料 |
|---|---|---|
| `case-real-yongkang/` | **三贏**（三視角全 ✅） | 需專案的 `data/`（未進版控） |
| `case-synthetic-nonwin/` | **非三贏**（縣市✅／腹地❌、接手方⚖️） | 自包含 |
| `case-decline-acquirer-holds/` | **市場衰退但接手方撐住** | 自包含 |
| `case-no-denominator/` | **不下定調**（四格全 ⬜） | 自包含 |

### 擴展（只在改到相關規則時跑）

| 目錄 | 分支／維度 | 什麼時候該跑 |
|---|---|---|
| `case-acquirer-broken/` | 接手方 ❌（版圖縮小） | 改版圖或效率證據 |
| `case-handover-failed/` | 易主失敗（❌❌） | 改定調表 |
| `case-cross-city/` | 接手方跨縣市，兩口徑方向相反 | 改「兩口徑」或效率證據 |
| `case-acquirer-sells-rival/` | 接手方同時是競品經銷商 | 改「值得續盯」或視角 3 定義 |
| `case-multi-store/` | 多據點同時易主，兩腹地方向相反 | 改腹地層或標的四詞 |
| `case-re-handover/` | 中途再轉手（18 個月三個經營者） | 改前後期窗口或模組 C |

合成案例由 `make_fixtures*.py` 產生、`verify_fixtures*.py` 驗算。**改資料後一定要重跑驗算**——首次產生 `case-handover-failed` 時，設計意圖是接手方 ❌，實際跑出來卻是版圖**擴大**（移轉進來的量補償了既有店的崩跌），驗算才抓到。**fixture 落在哪個分支要用算的，不能用想的。**

## 怎麼跑

給 agent 的 prompt 就是各案例 `expected.md` 開頭的「情境」段，**加上一句「依 skill 產出分析」**。

**不要**把 `expected.md` 的預期結果給 agent 看——那是答案。

> ⚠️ **`expected.md` 與 `reg.csv` 同目錄，agent 有能力自己讀到答案。**
> 實測中有 agent 主動聲明「全程未讀取同目錄下的 expected.md」——它自律了，但**下一個不見得會，而且你不會知道**。
> **穩妥做法：把 `reg.csv` 複製到 scratchpad，prompt 只指向那份副本。** 別讓測試的有效性取決於受測者的自制力。

跑完逐項對照 `expected.md` 的「必過項」。

## 判準：對「判定」，不對「數字」

- **判定**（三視角各自的 ✅/⚖️/❌/⬜、定調、標的四詞）**必須完全吻合**。
- **數字**允許因資料版本而變（真實資料會被重新匯出）。數字對不上時先查資料版本，不要急著改框架。

## 覆蓋率現況

定調表的 6 種組合**已全部覆蓋**：

| 分支 | 狀態 |
|---|---|
| 三贏 | ✅ `case-real-yongkang` |
| 品牌贏了但現場沒跟上 ＋ 接手方⚖️ | ✅ `case-synthetic-nonwin` |
| 市場衰退但接手方撐住 | ✅ `case-decline-acquirer-holds` |
| 接手方有問題（整體✅／接手方❌） | ✅ `case-acquirer-broken` |
| 易主失敗（❌❌） | ✅ `case-handover-failed` |
| 任一格 ⬜ → 不下定調 | ✅ `case-no-denominator` |

> **每個沒測過的分支都可能藏著洞——這句話每次都應驗了。**
> - 「超額成長貼錯層」在三贏案例上永遠不會出現（腹地與縣市同向），是換到非三贏案例才暴露的。
> - 「衰退市場用絕對量判有機成長」在成長市場看不出來（絕對量與市占同向），是 `case-decline-acquirer-holds` 才炸開的。
> - 「①a①b 皆不可得時該填什麼」只有在**完全沒有分母**的極端案例才會逼出來——`case-no-denominator` 的兩個 agent 在那一格判出相反答案。

**覆蓋率到頂不代表沒有洞。**

## 已驗證「沒有洞」的維度 ★

這一節和上面的覆蓋率表一樣重要——**它防止未來憑直覺往框架裡加規則**。

下列四個維度都是刻意設計來打破框架假設的，**全部 2/2 收斂，一條規則都沒加**：

| 維度 | 原本擔心什麼 | 實測結果 |
|---|---|---|
| 標的跨縣市 | 「兩口徑都要報」從沒被測過（前六案全部重合）；分歧時判定用哪個？ | **4/4** 一致用全部據點口徑判效率。連刻意讓兩路徑導向 ✅ vs ⚖️ 的尖銳版也不分歧 |
| 接手方賣競品 | 視角 3 預設接手方與品牌利益一致 | **2/2** 判定由效率證據獨立成立，衝突歸「值得續盯」 |
| 多據點同時易主 | 「腹地層」是單數欄位，裝不下兩個相反的結論 | **2/2** 合併判定＋拆開揭露分歧（沿用「兩層不同向」的既有模式） |
| 中途再轉手 | 同期 YoY 會整段跳過中間那一手 | **2/2** 自己判讀出兩次異動、分開歸屬、兩個窗口並列 |

**為什麼第一批（定調表 6 分支）修了 5 條，第二批（4 個結構維度）0 條？**
第一批測的是**框架直接規定的東西**——規定不全就是洞。第二批測的是**框架沒明寫的情況**，而分析者每次都用既有原則類推出答案：口徑並列、不同向就拆開、量體權重、證據門檻。

**好的規則集不是窮舉情況，而是給出可類推的原則。** 為每個新結構加一條規則，只會讓框架變胖，而且擋不住第五種沒想到的結構。

## 已知仍未測的

- 真實的**第二個**案例（不同縣市／品牌）。**合成資料的盲點是作者造的，作者造不出自己想不到的東西**——這比再加十個 fixture 有價值。
- 中性 prompt 的盲點測試：`case-acquirer-sells-rival` 那輪的 prompt 寫了「請自己盤點」，等於提示，沒有真正驗證「會不會自發發現」。
