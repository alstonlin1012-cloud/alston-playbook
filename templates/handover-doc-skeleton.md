# HANDOVER 骨架 — 低頻／一次性任務的交接入口

> 一次性任務（年度執行、季度盤點、換季調整）跟常態 pipeline 不同——頻率太低、容易被遺忘、原作者離職後接手的人沒 context。這份骨架設計為**新接手 15 分鐘讀完就會做**：為什麼讀 → 讀什麼順序 → 什麼時候做 → 怎麼確認環境對 → 問誰 → 歷年執行紀錄留痕。

## 情境（什麼時候拿出來用）

- **低頻任務**：年度一次、季度一次、換季一次（不像每日 pipeline 有肌肉記憶）
- **一次性 setup 麻煩**：需要 OAuth / 權限 / 特殊帳號，第一次做很卡
- **原作者離職或輪調**，下一任接手沒 context
- **業務後果大**：不做會造成業務停擺／資料斷層／客訴

**跟 [[report-maintenance-sop-skeleton]] 的差別**：
- 報表維運 SOP：**修**壞掉的東西（反應式）
- HANDOVER：**執行**低頻任務（主動式）

**跟 [[bi-knowledge-base-structure]] 的差別**：
- BI 知識庫結構：整個知識庫骨架
- HANDOVER：單一任務的入口文件

## 核心主張

**HANDOVER 不是「交接 checklist」，是「新接手 15 分鐘讀完」的入口文件**：

1. **預估時間承諾**：「全程預估 15 分鐘」（讓讀者知道投入成本）
2. **分層引導**：先讀什麼（第一次必讀） → 才讀什麼（要跑時再看） → 最後讀什麼（出事排查）
3. **檔案自己說自己要先讀**：`§2. 快速了解這件事（按順序看）`
4. **歷年執行紀錄留痕**：每次跑完填一次，當下一任的 context
5. **「問誰」依序遞升**：先讀文件、再 git log、最後才問人

## 骨架（八節）

### § 1. 你為什麼在讀這份

**一段話**說清楚三件事：
- 這份對應什麼任務
- 不做會發生什麼（業務後果）
- 誰會指派這件事

**範例**：
> 你被指派每年**把 100+ 家門市 Google Sheet 的日期範圍往下延伸一年**。
>
> 不做會發生什麼：門市店長跨年後打開 sheet 發現沒有新年度的格子可以填，業務停擺，Tableau 資料斷層。

**為什麼放第一節**：讓讀者**當場決定**要不要繼續讀下去。不是這任務的人立刻走開。

### § 2. 快速了解這件事（按順序看）

**關鍵段**：把後面每一節的閱讀順序寫出來，分三種情境：

```markdown
**15 分鐘版**（第一次接手必讀）：
1. 本份 HANDOVER.md（你正在看）
2. [runbook.md §0 快速總覽] — 1 分鐘知道 what/why/when
3. [runbook.md §1 開始前檢查清單] — 2 分鐘知道要什麼權限/環境

**要實際跑的時候才看**：
4. [runbook.md §2 一次性 Setup] — 第一次接手必做
5. [runbook.md §3 年度執行流程] — 真正跑的步驟

**要更深入 / 出事排查**：
6. [overview.md] — 整個 pipeline 的架構說明
7. [runbook.md §4 救援]、§5 rollback、§6 技術 quirk、§10 地雷
```

**為什麼要分三種情境**：
- 第一次接手讀太多細節會迷失
- 實際跑時只看執行步驟，不用再讀概念
- 出事時才需要深入 pipeline 架構

### § 3. 關鍵資訊速查

扁平列出**最常回來查**的東西：

- **執行者身份**：用哪個帳號、為什麼是這個帳號
- **憑證檔案位置**：絕對路徑 + chmod + 若遺失從哪補
- **專案位置**：code / docs / deps 在哪
- **相關系統**：GCP project / API / OAuth client / master sheet ID

**鐵則**：每項都要說「**如果遺失從哪補**」。不然下任重新 setup 時卡住。

### § 4. 什麼時候做這件事

寫明：
- **頻率**（每年 12 月中 / 每季末 / 季度開始前）
- **緩衝時間**（預留 2 週到 deadline）
- **前置依賴**（哪些東西要先準備好，哪些是人工維護）

**為什麼**：下任接手可能看到 `12 月中` 就想「現在才 10 月，不急」。寫「預留 2 週」讓他們知道真正的 deadline。

### § 5. 第一次接手的 checklist

**按順序打勾**：
```markdown
### 讀文件
- [ ] 讀完本份 HANDOVER.md
- [ ] 讀完 runbook.md §0-§1

### 取得權限 / 憑證
- [ ] 確認你能用 <執行帳號> 登入
- [ ] 確認帳號是 <某資源> 的 editor
  - 抽驗 3 個目標確認
  - 缺權限 → 聯絡前任 / IT
- [ ] 確認你能進 <GCP project>

### 環境
- [ ] clone 專案
- [ ] 本機裝依賴
- [ ] 憑證下載到正確位置、chmod 600

### 跑一次驗證 setup 對
- [ ] 跑 `--dry-run --limit 1`
- [ ] 看到 `Summary: ok=N skip=0 fail=0` = setup 完成

### 正式執行時
- [ ] 跟著 runbook §3 的 dry-run → 試跑 → 全批次 流程
```

**為什麼要有「跑一次驗證 setup 對」**：很多 setup 問題只有實跑才會出現（OAuth consent、權限、環境變數）。dry-run with limit=1 是最便宜的驗證方式。

### § 6. 不知道問誰？

**依序**（非平行）：

1. 讀 [runbook.md §4 的 fail message 對照表] — 90% 常見問題有答案
2. 讀 [runbook.md §10 地雷] 清單 — 避免重蹈覆轍
3. 讀 [overview.md §X 關鍵發現] — 了解設計時遇到的坑
4. git log / git blame 看前任留的 commit message
5. 問前任 / 團隊

**為什麼依序遞升**：
- 問人的成本最高、最慢
- 90% 問題在文件、git history 有答案
- 強制「先讀 → 再問」是對下一任好（而且下下任 setup 時前任也可能離職了）

### § 7. 歷年執行紀錄

**每次跑完填一次**：

| 年度 | 執行日期 | 執行者 | 總量 | 成功 | 失敗 | 備註 |
|------|---------|-------|------|------|------|------|
| 2027 | 2026-11-10 | 甲 | 100 | 100 | 0 | 首次 setup，code 3 輪迭代後 100% 自動化。總時間 ~27 分鐘。 |

**為什麼關鍵**：
- 下任知道「這任務通常要跑多久」
- 可以對比「這次比去年多失敗 X 件」
- `code 3 輪迭代` 這種備註直接告訴下任「這任務可能會踩雷、留緩衝」
- 執行紀錄本身也是 incident log（見 [[incident-log-management]]）

### § 8. 檔案地圖

```
<project>/
├── docs/
│   ├── HANDOVER.md               ← 你現在在這
│   ├── runbook.md                ← 執行手冊
│   └── overview.md               ← pipeline 架構 reference
├── src/
│   └── <main entry>.py
└── requirements.txt
```

**為什麼要畫**：手機或新環境打開 repo 時，一眼看出「哪個檔對應哪種需求」。

## 搭配 runbook：分工原則

HANDOVER 跟 runbook 是**兩份檔**，不要合併：

| 檔 | 回答什麼 | 讀者 |
|----|---------|------|
| **HANDOVER.md** | 「我該怎麼開始」 | **新接手**第一次讀 |
| **runbook.md** | 「我該怎麼做」 | **熟手**每次執行時翻 |

**鐵則**：HANDOVER 絕對不重複寫 runbook 的步驟——只**連過去**。否則兩處變更不同步，新手照舊文件炸掉。

### Runbook 的骨架（參考）

```
§0 快速總覽（30 秒讀完）
§1 開始前檢查清單
§2 一次性 Setup（第一次接手必做）
§3 年度執行流程（真正跑的步驟）
§4 救援（fail message 對照表）
§5 Rollback
§6 技術 quirk / 已知坑
§10 地雷（別做這些事）
```

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| HANDOVER 寫成 runbook | 新手讀完還是不知從哪開始 | 分兩份檔，HANDOVER 連過去 |
| 沒時間預估 | 新手不知道要投入多少 | § 1 寫「15 分鐘讀完」 |
| 不分閱讀情境 | 第一次接手讀太多細節 | § 2 分三層（第一次/執行時/出事） |
| 關鍵資訊沒說「遺失從哪補」 | 下任重新 setup 時卡住 | § 3 每項都寫補救路徑 |
| 沒 dry-run 驗證步驟 | 第一次正式跑才踩雷 | § 5 強制 `--dry-run --limit 1` |
| 「問誰」直接列人 | 下任直接 ping 前任（可能已離職） | § 6 依序遞升：先讀文件再問人 |
| 歷年執行紀錄空的 | 下任無法估工 | § 7 每次跑完**強制**填一次 |
| 執行紀錄只寫「成功」 | 下任不知道哪些難搞 | 備註要寫「3 輪迭代」「踩雷點」 |
| 權限抽驗寫「全部確認」 | 下任做不到會卡住 | 寫「抽驗 3 個」有具體步數 |
| HANDOVER 跟專案脫鉤 | 在 Google Doc 或私人筆記 | 寫在 `docs/HANDOVER.md`，跟 code 一起版本控制 |

## 檢核清單（HANDOVER 寫完前對一次）

- [ ] § 1 寫明任務 + 不做的後果 + 誰會指派？
- [ ] § 2 分「第一次必讀 / 執行時看 / 出事看」三層？
- [ ] § 3 的每項都寫「遺失從哪補」？
- [ ] § 4 寫明頻率 + 緩衝時間 + 前置依賴？
- [ ] § 5 checklist 分「讀文件 / 權限 / 環境 / 驗證跑一次 / 正式執行」？
- [ ] § 5 有包含 `--dry-run --limit 1` 的驗證步驟？
- [ ] § 6「不知道問誰」依序遞升（文件 → git log → 人）？
- [ ] § 7 有歷年執行紀錄表？（即使第一次執行也要填）
- [ ] § 8 檔案地圖畫了嗎？
- [ ] 跟 runbook 分兩份檔，HANDOVER 不重複寫步驟？

## 完整骨架（可改字複用）

```markdown
# HANDOVER — 新接手讀這份

> 這份是 **<專案名>** 的「第一次接手」入口文件。
> 讀完這一頁，你會知道要**做什麼、看哪份文件、問誰**。全程預估 15 分鐘。

## 1. 你為什麼在讀這份

你被指派<任務一句話>。
不做會發生什麼：<業務後果>。

## 2. 快速了解這件事（按順序看）

**15 分鐘版**（第一次接手必讀）：
1. 本份 HANDOVER.md
2. [runbook.md §0] — <一行說明>
3. [runbook.md §1] — <一行說明>

**要實際跑的時候才看**：
4. [runbook.md §2 一次性 Setup]
5. [runbook.md §3 執行流程]

**要更深入 / 出事排查**：
6. [overview.md]
7. [runbook.md §4-§10]

## 3. 關鍵資訊速查

### 執行者身份
- 用 <帳號>（為什麼是這個帳號：<理由>）
- 若無法登入 → <補救>

### 憑證檔案位置
- `<絕對路徑>`（chmod 600）
- 若遺失 → <補救路徑>

### 專案位置
- Code / Docs / Deps 路徑

### 相關系統
- GCP / API / 外部服務

## 4. 什麼時候做這件事

<頻率>，預留 <緩衝> 到 deadline。

前置依賴：<人工維護項>。

## 5. 第一次接手的 checklist

### 讀文件
- [ ] ...

### 取得權限 / 憑證
- [ ] ...（抽驗 N 個確認）

### 環境
- [ ] clone / 裝 deps / 憑證放對位置

### 跑一次驗證 setup 對
- [ ] `--dry-run --limit 1` → 看到 ok=N fail=0

### 正式執行時
- [ ] 跟 runbook §3

## 6. 不知道問誰？

1. 讀 [runbook.md §4] fail message 對照表
2. 讀 [runbook.md §10] 地雷清單
3. 讀 [overview.md] 關鍵發現
4. git log / git blame
5. 問前任 / 團隊

## 7. 歷年執行紀錄

| 年度 | 執行日期 | 執行者 | 總量 | 成功 | 失敗 | 備註 |
|------|---------|-------|------|------|------|------|

## 8. 檔案地圖

```<tree>```

---
**本份更新**：YYYY-MM-DD
**下次更新時機**：跑完一次後把實際跑時間、問題補到 § 7
```
