# AI × 人協作 PRD 骨架

> 跟 AI 一起做一個有多階段、涉及人工判斷的專案時（寫文件、做影片、建系統），最常見的翻車是「AI 以為可以直接動、人以為 AI 會停下來等」。這份 PRD 骨架強制每個 phase 明示**執行者、輸入、輸出、是否人工 checkpoint、AI 不能做什麼**——讓雙方預期對齊，不要走到最後才發現方向錯了。

## 情境（什麼時候拿出來用）

- 專案有**多階段**，不是一條線的實作
- 每階段**不同人做**：有 AI 做的、有人做的、有 AI + 人協作的
- 有些動作一旦做了**不好回頭**（渲染影片、寄信、部署）
- 怕 AI 自己往前衝而沒等人工確認
- 要把專案當作**產品需求**寫下來，讓下一任接手能照做

**跟 [[handover-doc-skeleton]] 的差別**：
- HANDOVER：**已經做過**的任務交接給下一任
- AI × 人協作 PRD：**新專案**的執行藍圖（告訴所有參與者這次怎麼走）

## 核心主張

**每個 phase 強制明示五件事**：

1. **執行者是誰**（AI / 人 / AI + 人）
2. **輸入是什麼**（上一 phase 的具體產出，不是「相關資料」）
3. **輸出是什麼**（檔名或具體產物）
4. **checkpoint 是否人工必確認**（用 ✋ 符號標示）
5. **AI 不能做什麼**（破壞性 / 不可逆動作明文禁止）

**核心鐵則**：**AI 做完 phase N 就停**。是否進 phase N+1 由人決定。

## 骨架（文件章節）

### § 1. 專案概覽

**三件事**：目標、最終交付物、不在此 PRD 範疇內。

```markdown
### 目標
<一段話，寫業務目標不是技術目標>

### 最終交付物

| 交付物 | 格式 | 用途 |
|--------|------|------|
| <產物 A> | `.md` | <用在哪> |
| <產物 B> | `.mp4` | <用在哪> |

### 不在此 PRD 範疇內

| 排除項目 | 原因 |
|---------|------|
| APP 本身的開發與測試 | 屬於工程團隊範疇 |
| Email 寄送系統的建置 | 假設寄送工具已存在 |
```

**為什麼要「不在此範疇」段**：
- AI 看到大目標容易把所有事都接起來做
- 明說排除 → AI 不會自己開「順便」去實作旁枝

### § 2. 執行階段總覽（核心表格）

**一張表看整個專案**：

```markdown
| Phase | 名稱 | 執行者 | 依賴 | Checkpoint |
|-------|------|-------|------|-----------|
| 1 | 需求盤點 | AI | 人提供原始資料 | - |
| 2 | 策略決定 | AI 草稿 → 人確認 | Phase 1 | ✋ 必須人工確認 |
| 3 | 內容生成 | AI | Phase 2 | - |
| 4 | 試做 | AI 寫 code + 人預覽 | Phase 3 | ✋ 必須人工 Studio 確認 |
| 5 | 衍生產出 | AI | Phase 4 | - |
| 6 | 整合發送 | 人 | Phase 5 | ✋ 必須人工確認 |
```

**關鍵欄位**：
- **執行者** 用「AI」/「人」/「AI 草稿 → 人確認」/「AI 寫 code + 人預覽」四種形態講清楚
- **Checkpoint** 用 ✋ 符號標人工必確認的 phase（通常是：決策點、不可逆動作點、交付外部點）
- **依賴** 寫前置 phase（讓 AI 不會跳步）

### § 3. 每個 phase 的四件事

每個 phase 統一結構：

```markdown
## Phase N：<名稱>

### 基本資訊

| 項目 | 內容 |
|------|------|
| 目標 | <一句話> |
| 執行者 | AI / 人 / 混合 |
| 輸入 | `<上一 phase 的具體檔名>` |
| 輸出 | `<這 phase 要產出的具體檔名>` |

### 執行步驟

| 步驟 | 動作 | 執行者 |
|------|------|-------|
| 1 | <第一個動作> | 人 |
| 2 | <第二個動作> | AI |
| 3 | 確認 | 人 |

### <這次的具體內容>

<這 phase 本次的實際填充——例如功能清單、溝通策略、腳本內容>

### 驗收標準

| # | 標準 | 狀態 |
|---|------|------|
| 1 | <可驗證條件 1> | ✅ |
| 2 | <可驗證條件 2> | ✅ |
| 3 | <可驗證條件 3> | ✅ |
```

**為什麼統一結構**：
- AI 一眼就能定位當前 phase 在哪
- 人 review 時結構一致、不用重新學每 phase 格式

### § 4. AI 不能做什麼（明文禁止）

**鐵則**：有**不可逆動作**（渲染輸出、寄信、deploy、grep delete）的 phase，**在 phase 內明文禁止**：

```markdown
> **AI 不自動執行 `npx remotion render`**。AI 只負責同步程式碼到 Studio 可預覽狀態；
> MP4 是否輸出、何時輸出，由負責人在 Studio 確認影片無誤後自行決定。
```

**為什麼要明文**：
- 「不可逆」+「AI 自主」= 災難
- 明文禁止 = AI 讀 PRD 時就會看到，不用猜
- 這一條是 CLAUDE.md 全域規約的具體化（見 [[claude-md-navigation-pattern]]）

**常見「AI 不能做」清單**：
- 渲染／輸出最終產物（影片、PDF）
- 寄 email / 發 Slack / 推訊息
- 部署到 prod / 執行 deploy script
- 跑生產資料 pipeline（會蓋線上）
- `git push` / `git force-push`
- 刪除檔案 / drop table

## Checkpoint 設計原則

**什麼時候要 ✋ 人工 checkpoint**：

| 情境 | 為什麼 |
|------|-------|
| **決策點** | 選方向 A 還是 B，AI 不該替人決定 |
| **不可逆動作點** | 一旦執行無法回頭 |
| **交付外部點** | 要給別人看之前，人要先看 |
| **跨 phase 關鍵輸出** | 後面 phase 依賴這份產物正確性 |

**不需要 ✋ 的情境**：
- 中間草稿階段
- 純技術執行（生 SQL、組 prompt）
- 可以多試幾次的生成

**鐵則**：checkpoint 太多 → AI 每步都停、人煩；太少 → 錯了才發現太晚。**三到四個 checkpoint 剛好**（總 phase 數 6-8 的話）。

## 修改對應表（長專案維護好用）

phase 做完後，**最常被問**的是「我想改 X，去哪改」。PRD 結尾放一張表：

```markdown
### 修改對應表

| 想改的東西 | 對應檔案 |
|-----------|---------|
| 投影片順序 / 圖片 / 時長 | `src/<Comp>/index.tsx` → `SLIDES` 陣列 |
| 轉場時間（OVERLAP） | `index.tsx` 第 6 行 & `SlideScene.tsx` 第 33 行（兩處要同步） |
| 開場標題 | `src/<Comp>/Intro.tsx` |
| 結尾文字 | `src/<Comp>/Outro.tsx` |
| 新增素材 | 放到 `public/<assets>/`，再加到陣列 |
```

**為什麼關鍵**：
- 專案做完後，**改需求**比重新開更常見
- AI 每次要改都要先 grep 一輪 → 慢、易改錯地方
- 這張表是**維護時最省時**的一節

## 「負責人」vs「AI」vs「AI 草稿 → 負責人確認」

**三種角色明確劃分**：

| 標記 | 意思 |
|------|------|
| **AI** | AI 自己做完整個動作，產出直接進下一步 |
| **負責人** | 完全人工，AI 不插手 |
| **AI 草稿 → 負責人確認** | AI 做初版，**必須**等人簽核才能往下 |
| **AI 寫 code + 負責人預覽** | AI 產出可預覽狀態，人用工具確認後決定是否繼續 |

**鐵則**：中間態要寫清楚是哪種。模糊的「AI 協助」容易變成「AI 自作主張」。

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 沒寫「不在範疇內」 | AI 把旁枝順便做 | § 1 排除項目列清 |
| 沒 § 2 總覽表 | AI 跳 phase 或漏 phase | 強制一張表看整個流程 |
| Checkpoint 全放 | AI 每步停、人煩 | 3-4 個關鍵 checkpoint |
| Checkpoint 全不放 | 跑到最後才發現方向錯 | 決策點 / 不可逆 / 對外都要 |
| 執行者寫「AI 協助」 | 混淆、AI 自主越界 | 四種角色標記 |
| 不可逆動作沒明文禁止 | AI 自己 render、deploy | § 4 明文禁止 |
| 驗收標準寫「看起來 OK」 | 事後扯皮 | 寫可驗證條件 |
| 沒修改對應表 | 維護時 AI 每次 grep | 結尾放表 |
| phase 輸入寫「相關資料」 | AI 猜不出要讀哪 | 寫**具體檔名** |
| phase 輸出寫「報告」 | AI 不知道產什麼格式 | 寫 `.md` / `.mp4` 等具體 |
| 每 phase 格式不一樣 | AI 跟人都要重新學 | § 3 統一骨架 |
| 「AI 全自動」想一次搞定 | 跑偏回不來 | 必備 checkpoint |

## 檢核清單（PRD 寫完前對一次）

- [ ] § 1 有「不在範疇內」段？
- [ ] § 2 執行階段總覽表齊全（Phase / 名稱 / 執行者 / 依賴 / Checkpoint）？
- [ ] Checkpoint ✋ 落在 3-4 個關鍵 phase？
- [ ] 每個 phase 有統一的四件事（目標 / 執行者 / 輸入 / 輸出）？
- [ ] 每個 phase 有執行步驟表（步驟 × 動作 × 執行者）？
- [ ] 每個 phase 有驗收標準表（可驗證條件）？
- [ ] 有不可逆動作的 phase 有明文「AI 不自動 X」？
- [ ] 執行者用四種角色標記（AI / 人 / AI→人 / AI+人）？
- [ ] 輸入 / 輸出都是具體檔名，不是「相關資料」？
- [ ] 結尾有修改對應表？

## 一句話總結

> **AI × 人協作最大的坑是「預期沒對齊」**。PRD 強制每 phase 明示執行者 / 輸入 / 輸出 / checkpoint / AI 不能做什麼——AI 做完就停、人決定是否進下一 phase，不走到最後才發現方向錯了。
