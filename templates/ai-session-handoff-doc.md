# AI session 交接文件骨架

> 跟 AI agent 做長期專案常遇到：這個 session 討論完了、context 快滿、要收尾。但下個 session 不會記得前面討論了什麼。這份骨架處理「session 跟 session 之間」的交接——不是給新人接手（見 [[handover-doc-skeleton]]），是給**下個 AI session 繼續寫**。11 節把討論結果、決策、待辦、偏好、參考檔案一次打包，讓下 session 冷啟動 10 分鐘內就能動工。

## 情境（什麼時候拿出來用）

- 跟 AI agent（Claude / Gemini）做長期專案
- 一個 session 討論完方向但沒寫完 code
- Context 快滿、要開新 session 繼續
- 多人輪流跟同個專案工作（session 不同 agent 也不同）
- 想避免「下 session 問一樣的問題」浪費時間
- 要把「這個 session 已經討論完的決策」固化下來

**跟 [[handover-doc-skeleton]] 的差別**：
- HANDOVER：**下任新人**接手，面向人
- 這份：**下個 AI session** 繼續，面向 AI agent
- 兩份精神相同（省啟動成本）但受眾與格式不同

**跟 [[claude-md-navigation-pattern]] 的差別**：
- CLAUDE.md：**常態**的 repo 入口（repo 一直在，agent 一直來）
- 這份：**一次性**的 session handoff（寫完下 session 讀一次用完）

## 核心主張

**AI session handoff 是「context pack」，不是 README**：

- 目標：下 session 冷啟動 10 分鐘內能接著動工
- 內容：**這 session 討論完的決策** + **下 session 要做什麼** + **使用者偏好** + **待確認項**
- 位置：專案的 `_working/<topic>-plan.md` 或 scratchpad
- 壽命：下 session 動完工就過期（不是長期文件）

**鐵則**：寫這份文件時就當「下個 session 什麼都不知道」—— 所有參考檔案絕對路徑、所有討論結果**結論在前推論在後**、所有待辦明確到「要問誰」。

## 骨架（11 節）

### § 1. 目標

**一段話**。寫「下 session 要達成什麼」—— **不是** 這個專案的終極目標、**是**下個 session 的範圍：

```markdown
## 1. 目標

- **新增** 2 支 datasource 說明頁：`Dev_Prospect_Contact`、`RS_DailyPromotion_2y_Rec`
- **深化** 既有 5 頁 + 2 新頁，目標：**使用者看完能照著在 Tableau 拉報表做分析**
- **新增** 典型分析場景段（在 `01_data_sources/index.md`）
```

**要點**：
- 用「新增 / 深化 / 修正」動詞開頭
- 具體到檔案層級
- 不寫「改善使用者體驗」之類抽象目標

### § 2. 受眾 / 驗收

**鐵則**：驗收標準要**可驗證**，不要抽象：

```markdown
## 2. 受眾 / 驗收

- 主受眾：**BI / BP analyst**（含新人 onboarding）
- 驗收標準：**新進員工能透過 playbook 找到對的資料源 + 對的欄位，自己去拉報表**
- 試讀者：使用者本人
```

**可驗證 vs 不可驗證**：
- ✅ 「新人能找到對的資料源、自己拉報表」
- ❌ 「資料源 playbook 完整」

### § 3. 現狀

**一段話 + 列表**，把下 session 進來會看到什麼寫清楚：

- 專案位置（**絕對路徑**）
- 技術 stack
- 已有的檔案列表（**用途一行**）
- 模板結構（如果有）
- 已有慣例（下 session 要遵守的）

**關鍵**：絕對路徑，不要相對。下 session cwd 不一定一致。

### § 4. 核心內容（這個 session 討論出來的）

這節是**核心**。把 session 討論的方向、分類、模式寫下來：

```markdown
## 4. 三個典型分析場景

### 場景 1：<場景名>
- **情境**：<新人會怎麼問>
- **datasource**：<要用哪幾個>
- **關鍵問題**：<需內部確認的事>
```

**鐵則**：
- 用**編號條列**不用散文
- **結論在前**，推論在後
- **「需內部確認」明寫**（下 session 就知道要再問使用者）

### § 5. 模板 / 格式規範

如果這 session 定下了格式規範，**完整寫出**：

```markdown
## 5. 場景段模板

​```markdown
### 場景 N: <場景名>

**問題描述（新人情境）**

**要用哪些 datasource**
- [連結](path.md) — 用途

**關鍵 join**
- key 名稱、1:N or 1:1、時間窗、陷阱

**關鍵欄位組合**

**Tableau 實作**
- ...

**已知陷阱 / FAQ**
​```
```

**要點**：
- 用 code block 包起來（下 session 直接複製）
- 模板要**可直接套用**，不是說明「你可以這樣寫」

### § 6. 動工順序（Phase / 輪次）

**鐵則**：明確分階段，每階段獨立可驗收：

```markdown
## 6. 動工順序

**第 1 輪：<主題>**
1. 寫 X（新，完整三段式）
2. 補 Y 的某段
3. index.md 新增某章節
4. 使用者自試讀，照文件在 Tableau 做一次
5. 定下模板

**第 2 輪：<主題>**（集大成）
1. ...

**估**：28-38 小時 ≈ 1-1.5 週全職
```

**要點**：
- 估時間（下 session 跟使用者可以同步預期）
- 每階段最後一步是「試讀 / 驗收」
- 第一輪完成才做第二輪（不要跳步）

### § 7. 必答清單（下 session 開工前要先確認）

**鐵則**：**「寫頁前必須先內部確認，不要邊寫邊猜」** —— 列具體問題：

```markdown
## 7. 新 datasource 頁必答清單

寫頁前必須先內部確認，不要邊寫邊猜。

**`RS_DailyPromotion_2y_Rec`**
1. 一列代表什麼？（促案 / 促案 × 品 / 促案 × 日）
2. 跟 `RS_DailyOrder` 的 join key 名稱 + 1:N 還是 1:1
3. 促案類型分類（搭贈 / 折扣 / 零利率 / …）怎麼標
4. 一單用多促案怎麼表達
5. 狀態時點（當時的 / 擷取當下）
```

**為什麼這節關鍵**：
- 下 session 最容易踩的坑是「邊寫邊猜」
- 具體到「要問 BI 哪一題」最省時間
- 把這些題目列出來，下 session 可以一次問完使用者

### § 8. 外部資源 / 輸入需求

```markdown
## 8. Workbook 需求（使用者會下載給下 session）

**第 1 輪需要：3 支**
- 促案效果分析 workbook
- 日銷售報表 workbook
- 促案月報 workbook

**挑選原則**：複雜度高、代表性強、近期有維護的。各 3-6 支就夠，不要全給。

**給檔形式**：
- 最佳：`.twb`（不用 `.twbx`，extract 太大）
- 命名建議：`promo/promo_effectiveness_v3.twb`

**Workbook 能加速的部分**
- 完整 Schema（欄位名 / 型別）
- Calculated field 公式
- 實際 join 寫法

**Workbook 補不了的**（仍需人工確認）
- 顆粒度、必做篩選、狀態時點、可回溯性
- 促案類型分類、attribution 邏輯等業務設計
- → 新頁必答 N 題仍需使用者回答
```

**要點**：
- 寫明「能加速什麼」「補不了什麼」
- 下 session 不會以為「拿到 workbook 就萬事 OK」

### § 9. 使用者偏好 / 本 session 已確認

**鐵則**：這節是**所有已拍板的決策**。下 session 不要再提：

```markdown
## 9. 使用者偏好 / 本 session 已確認

1. 場景段放 `index.md` 同檔多章節，**不開 scenarios/ 資料夾**
2. 場景段**要寫 Tableau 實作細節**（calculated field / filter 範例 + workbook 連結）
3. Dev_Prospect_Contact 的 **PII 疑慮暫時忽略**
4. 車款資訊**只用 RS_DailyOrder 欄位**，先不跨源
5. 試讀者 = 使用者本人
```

**要點**：
- 條列**不要散文**
- 每條都是「下 session 不要重問」
- 「暫時忽略」/「先不」這類字眼明寫範圍

### § 10. 動工前最後確認（待使用者答）

下 session 一開場要問的題：

```markdown
## 10. 動工前最後確認（待使用者答）

1. 工作放哪 branch？（建議 `feat/datasource-playbook`）
2. 9 題必答清單腦袋有幾題有答案？沒答案的要先 Slack 問 BI
3. 場景 1「baseline 怎麼定」有共識嗎？
4. Tableau 實作範例抓多細？
```

**要點**：
- 題目**具體**（不是「你有什麼想法」）
- 附**建議答案**（降低使用者思考成本）
- 這節是下 session 開工前的最後一個 checkpoint

### § 11. 業界參考 / 風險 / 相關檔案

**鐵則**：把**為什麼這樣設計**的業界參考寫在這 —— 未來有人挑戰時可以直接引用：

```markdown
## 11. 業界參考（為什麼這樣設計）

- **Amundsen / Airbnb Dataportal / Spotify Lexikon**：catalog 以使用頻率排序
- **DataHub**：Tableau 原生 connector，但自架重，對本場景 overkill
- **大廠共識**：**欄位語意描述沒有自動化解法**，只能靠人工補

## 12. 風險 / 注意

- **寫前先內部跑一次場景模擬**：挑場景 1 自己在 Tableau 完整做一次
- **LLM 不自動 merge**：核心價值的段永遠 human review
- **不追求 100% 覆蓋率**：top 10-15 寫深比 50 支寫淺有用

## 13. 相關檔案

- 本計畫：`<絕對路徑>`
- 目標 repo：`<絕對路徑>`
- 關鍵既有頁：`<絕對路徑>`
- 模板參考：`<絕對路徑>`
```

## 什麼是「好的 handoff」vs「壞的 handoff」

### 好的 handoff
- 下 session 讀完 10 分鐘內能動工
- 所有決策寫在 § 9（下 session 不會重問）
- 待辦明確到「要問誰、問哪題」（§ 7、§ 10）
- 絕對路徑、具體檔名

### 壞的 handoff
- 散文 narrative（下 session 要花時間拆重點）
- 「大概要這樣做」沒明確到可執行
- 相對路徑（下 session cwd 不一致就找不到）
- 沒 § 9「已拍板」—— 下 session 會重問同樣的題
- 沒估時間 —— 使用者不知道投入多少

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 散文 narrative | 下 session 要拆重點 | 編號條列 |
| 相對路徑 | cwd 不同找不到 | 絕對路徑 |
| 沒「已拍板」節 | 下 session 重問 | § 9 條列所有決策 |
| 必答清單抽象 | 「業務邏輯要確認」 | 具體問題「一列代表什麼」 |
| 沒估時間 | 使用者不知投入多少 | § 6 每輪附估時 |
| 沒試讀步驟 | 做完才發現方向錯 | 每輪最後是「使用者試讀」 |
| 一次講太多 session | 範圍失焦 | 這份只管「下一個」session |
| 寫成常態文件 | 跟 CLAUDE.md 混淆 | 放 `_working/` 標明一次性 |
| 「以後再議」條目 | 下 session 不知該不該碰 | 明說「本 session 不處理」 |
| 使用者偏好寫成「建議」 | 下 session 又討論一次 | 「已拍板」用肯定語氣 |
| 動工順序無驗收 | 做完不知對不對 | 每輪一個「試讀」步驟 |
| 外部資源寫「拿到就萬事 OK」 | 下 session 以為夠了 | 明寫「能加速 vs 補不了」 |
