# 目的性抽樣驗證系統報表

> 想驗證系統給的數字準不準時，第一個誘惑是「隨機抽樣」。結果拿到「差了 15%」——沒人知道**為什麼差、哪種情境差得多、能不能改善**。這份 methodology 改走**目的性抽樣**：刻意挑樣本讓每一種可能出錯的情境都至少被看到一次。

## 情境（什麼時候拿出來用）

- 系統給了一個數字，沒人實際驗證過它準不準（traffic、計數、分群、評分）
- 驗證成本高（要人工對照、派人力觀察、手動對帳）
- 樣本太多無法全驗
- 業務決策壓在這個數字上
- 要搞清楚**「偏誤哪裡來」**，不只是「偏誤平均多少」

## 核心主張

**驗證系統報表要用目的性抽樣（purposive sampling），不是隨機抽樣**：

- 隨機抽樣回答「平均準度是多少」→ 得到一個無法行動的數字
- 目的性抽樣回答「什麼情境下系統會錯、能不能改善」→ 得到可以 patch 的洞察

**鐵則**：驗證系統可靠度 ≠ 抽樣估計母體。前者要「挑能測出破洞的樣本」，後者要「代表性樣本」。兩種抽樣學目標完全不同。

## 骨架（九節）

### § 1. 為什麼要做（四欄：現況 / 核心問題 / 要達成 / 怎麼做）

**鐵則**：第一節就把「業務動機」講清楚，不要先講方法。

```markdown
| 項目 | 內容 |
|------|------|
| 現況 | 系統只給一個 X 數字，沒有人實際驗證過準不準 |
| 核心問題 | 這份報表有多少水分沒人說得出來。數字不能信，<下游決策>就跟著失準 |
| 這次要達成 | 一、算出系統數字的水分有多大；二、看清楚<定性維度>的實況 |
| 怎麼做 | 派<人力>做<對照動作>，跟系統同時段數字對照，差距就是水分 |
```

### § 2. 前提（不能做的事）

列**明確不做**的事，避免事後被挑戰：

| 前提 | 為什麼 |
|------|-------|
| 不能隨機挑 | 隨機抽只會得到「差了 X%」這種數字，不知道為什麼差、哪種情境差得多、能不能改善 |
| 不同版本系統要分開驗 | 樣本群不重疊時只能各自算完並列比較，不能直接比對 |

### § 3. 選樣的四個條件（核心）

**四個條件都是為了讓結果能解釋原因，而不只是得到一個平均值**。

| 條件 | 要達成什麼 | 怎麼設定 |
|------|-----------|---------|
| **版本都要驗** | 知道哪一套比較準 | 每版本抽 N 個 |
| **極端 + 正常都要** | 分辨水分是**系統性問題**還是**個別樣本故障** | 挑最誇張的、同時挑最穩定的當對照 |
| **情境均衡分布** | 避免結論被單一情境拖累 | 按地區 / 時段 / 類型平均分 |
| **訊號量要夠大** | 觀察效率 | 設閾值篩掉太小的樣本 |

**要點**：
- 「極端 + 正常」的對照組是**核心設計**——沒對照組，分不出系統問題跟個案問題
- 情境均衡不是為了「具代表性」，是為了「避免結論被單一情境拖累」
- 訊號量閾值是**實驗效率**議題，不是代表性議題

### § 4. 定義「極端」的判準（別被規模干擾）

**陷阱**：選「波動大的樣本」時，小樣本本來就容易波動——這是統計必然，不是系統問題。

**修正判準**：**波動大到無法用規模小解釋，才算可疑。**

**範例**：
```
日均 X 人的樣本每日波動 ±Y 人 → 檢查 Y/X 比率
若波動大的樣本中，Z% 都是小樣本 → 門檻改成「波動大 + 規模也大」才算可疑
```

### § 5. 選樣結果 + 覆蓋檢查

列出最後選的樣本，附：
- **選它的理由**（跟 § 3 的哪個條件對上）
- **覆蓋檢查**：每個軸都滿足分布嗎？

```markdown
| 區 | 樣本ID | 類別 | 日均 X | 波動度 | 選它的理由 |
|----|--------|------|--------|--------|-----------|
| 北 | A | v1 | 240 | **218%** | 全公司波動最誇張。對照：同區最穩定的 B |
| 北 | B | v2 | 233 | **8%** | 全公司最穩定。與 A 同區同規模，互為對照 |

**覆蓋檢查**：v1/v2 各 X 個；北中南各 X 個；日均 X-Y 全數達標；類型 GS/RS 分別 X/X。
```

### § 6. 最值得報告的觀察點（3 個）

從選定樣本中挑 3 個組合，每個講：

| 組合 | 發現 | 為什麼重要 |
|------|------|-----------|
| 1 | 兩個同條件樣本波動差 10 倍 | 條件、規模、版本全部相同，唯一不同的是系統在這兩個樣本的表現，沒有其他解釋空間 |
| 2 | 某樣本波動超過合理範圍 | 可能是斷訊、重複計數、資料品質問題 |
| 3 | 某樣本幾乎不動 | 系統是不是其實輸出平滑後的估算值？若是，影響範圍遠大於個案 |

**設計要點**：排名「若時間只夠報一個發現，報哪一個」——這是給管理層的可讀性設計。

### § 7. 工時配置（尖峰 vs 離峰都要看）

**鐵則**：觀察要包含**兩種時段**——不同時段測出不同性質的錯。

| 時段 | 檢出什麼錯 |
|------|-----------|
| **離峰** | 「多算」的錯誤（路過者被計入、店員被計為客人）。在尖峰會被真實流量蓋過 |
| **尖峰** | 「少算」的錯誤（擁擠時系統漏計） |

**結論**：少看任一種就會漏掉一半的水分來源。

### § 8. 已知限制 + 妥協

在找不到理想樣本的區域（例：中區四個條件都滿足的太少），**不要硬選**：

| 項目 | 內容 |
|------|------|
| 問題 | 中區四個條件交集的樣本太少 |
| 原因 | 符合門檻的樣本都屬穩定型；波動大的樣本都不達規模門檻 |
| 建議處理 | 將中區定位為「**正常基準區**」，負責回答「連正常樣本都有多少水分」，波動對比交由其他區承擔 |
| 替代方案 | 放寬規模閾值，但觀察效率下降 |

**鐵則**：妥協要明說。讓中區變成「正常基準」不是 bug，是設計。

### § 9. 能回答什麼、不能回答什麼（誠實邊界）

**鐵則**：這一節絕對必備——否則結論會被挑戰到爆。

**能回答**：
- 哪一種情境下系統數字水分大
- 水分是**系統性問題**還是**個別樣本故障**
- 哪個版本比較接近實際

**不能回答**：

| 項目 | 說明 |
|------|------|
| 全母體的水分率 | N 個樣本是刻意挑選而非隨機抽樣，結論是「哪種樣本水分大」，不是「母體水分 X%，誤差 ±Y%」。要講母體數字需另設計隨機抽樣，樣本量也要大幅增加 |
| 稀有類別的整體狀況 | N 中稀有類別只 K 個，不足代表 |
| 版本間精確歸因 | 兩版本樣本零重疊時，只能各自算後並列比，差異可能來自版本本身，也可能來自兩批樣本條件不同 |

## 需要裁示的事項

**鐵則**：每份報告結尾列「需要裁示」兩到三件：

| # | 決策項目 | 建議 | 影響 |
|---|---------|------|------|
| 1 | 是否先拉更長期資料重新確認名單 | **建議做** | 短期資料易被偶發事件扭曲，拉長資料約 X 天，但可避免選錯樣本 |
| 2 | 是否接受某區「缺少對比」的限制 | **建議接受** | 硬找會降低觀察效率 |

**為什麼**：
- 讓決策者**明確做決策**，不要給「你看著辦」的空間
- 附「建議」讓決策成本最低
- 附「影響」讓決策者知道風險

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 隨機抽樣驗證系統 | 得到「差了 X%」無法行動 | 改目的性抽樣 |
| 只挑最誇張的 | 分不出系統性 vs 個案 | 加「正常對照組」 |
| 「波動大 = 可疑」直接套 | 把小樣本統計必然誤判成系統問題 | 「波動大到規模不能解釋」才算可疑 |
| 只看尖峰時段 | 漏「多算」的錯 | 尖峰 + 離峰都要看 |
| 只看離峰時段 | 漏「少算」的錯 | 同上 |
| 兩版本直接比平均 | 零重疊時結論不成立 | 各自算後並列、明說不能直接比 |
| 缺樣本區硬塞 | 樣本品質下降 | 妥協改定位「正常基準區」 |
| 結論沒邊界段 | 被老闆用「母體水分率」挑戰 | § 9 明寫「能答/不能答」 |
| 沒列裁示項 | 報告變「你看著辦」 | 結尾列 2-3 個裁示 + 建議 + 影響 |
| 把驗證結果外推全母體 | 「全公司水分 X%」 | 目的性抽樣的結論是「哪種情境水分大」 |

## 一句話總結

> **要驗證系統準不準，不是估計母體，是找破洞**。目的性抽樣的四條件（版本 / 極端對照 / 情境均衡 / 訊號量）讓每種可能失效的情境都至少被看到——結論從「平均 15%」升級成「哪種情境下系統會錯、能不能改善」。
