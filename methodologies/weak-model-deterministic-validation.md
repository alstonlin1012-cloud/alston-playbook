# 弱模型 + 確定性驗證 methodology

> 用弱模型（flash / mini / nano）做 NL→SQL、NL→Function、NL→任何 structured action 時，傳統做法是「讓模型更聰明（換大模型、加 reasoning）」。這份 methodology 走另一條路：**讓模型不容易錯，錯了程式當場抓到**。核心原則——**弱模型「說自己讀到哪些條件」的可靠度，遠高於「判斷自己有沒有做對」**。

## 情境（什麼時候拿出來用）

- 要用成本考量的弱模型（flash-lite / haiku / nano）做 structured task
- 任務是**翻譯型**（NL→SQL、NL→function call、NL→DSL）不是推理型
- 錯誤樣貌是「有來源、但來源答非所問」—— 不是幻覺，是**悄悄漏條件**
- 想升級到大模型不划算、不敢（prod 上線、單次 cost 要低）
- 已踩過「叫模型自檢它說自己沒錯」的坑

## 核心主張

### 原則 1：不要求模型聰明，只要求它把自己讀到的東西講出來；對不對，由程式判斷

弱模型「**說出自己讀到哪些條件**」的可靠度，遠高於「**判斷自己有沒有做對**」。所以：

1. **讓它不容易錯** — 給它一條好走的路（子查詢樣板、few-shot），而不是一堆要它自己推敲的規則
2. **錯了要當場抓到** — 用確定性的程式碼驗證它的輸出，不靠它自省
3. **反問是最後一道防線，不是第一道** — 而且觸發權在程式手上，不在模型手上

### 原則 2：「有來源但答非所問」比「無中生有」更危險

幻覺（無中生有）有大量 systemInstruction 可擋。真正難擋的是：
- SQL 跑得過
- 數字回得來
- 但問的是「A 店 6 月賣幾台」，SQL 卻漏了門市過濾 → 回答**全公司**數字

這種錯**看起來完全合規**，不崩潰、不報錯、不拒答。弱模型 + 大 context 下必然會偶發。

### 原則 3：「讓不確定時反問」不能當主力

討論時常有人提「叫模型沒把握就反問」。**這條對已證實的錯誤無效**：
- 錯誤 SQL 跑得過時，模型**並不覺得自己不確定**
- 「叫一個不知道自己錯的模型舉手，它不會舉手」
- 反問調鬆 → 對本來答得出的問題也反問 → 使用者抱怨
- 補丁通常演化成「不要為了保險過度反問」—— 這本身就是被咬過的疤

反問機制保留，但由**程式的確定性驗證**觸發，不由模型自覺觸發。

## 四階段骨架（從 prompt 到結構防腐）

### 階段 1 — 讓它不容易錯（純 prompt）

**目標**：降低錯誤率。改動集中在 prompt，一次做得完，風險低。

- **給可以照抄的樣板**：子查詢範例、few-shot（跨表 + 單表各一）
- **明文禁止易錯的 pattern**（例：禁用裸 JOIN 以免一對多膨脹）
- **把軟性建議改成硬性規則**（「必須 JOIN」→「必須用這個子查詢形式」）
- **別忘了模糊比對**（名稱比對一律 `LOWER(...) LIKE LOWER('%...%')` 不要精確 =）
- **回答階段加守門**：核對產出的 SQL 是否含問題中的條件，不符就不得當答案

**陷阱**：這階段**不要**叫模型「先列出條件再自我檢查」。弱模型會把檢查清單一起吐出來，污染輸出。自檢要做，但用階段 2 的方式做。

**驗收**：重現已知錯誤案例，確認修好。再試單表問題確認沒改壞。

### 階段 2 — 錯了當場抓到（structured output + 程式驗證）

**目標**：**維持弱模型的核心保險**。階段 1 只降低錯誤率，階段 2 才真正把關。

1. **模型回 structured output**，不只是 raw SQL：

```json
{
  "needsQuery": true,
  "conditions": [
    {"type": "store", "value": "A店"},
    {"type": "month", "value": "202506"},
    {"type": "product", "value": "甲車"}
  ],
  "sql": "SELECT ..."
}
```

2. **程式端逐一驗證**：每個 condition 的 value 是否真的出現在 `sql` 字串裡
   - `A店` 不在 sql → 程式當場知道漏了
   - **不需要模型自省**

3. **缺了就自動重試一次**，帶上「你漏了門市條件」的明確提示
   - 弱模型便宜，重試成本可忽略

4. **重試還是漏 → 這時才反問使用者**，有根據的反問：
   - 「我沒辦法正確查到 A 店，你要不要換個問法」
   - 不是模型憑感覺瞎問

5. **`needsQuery: false` 當 escape hatch**：讓模型判「這題不用查」（問定義、問建議、問解讀），直接跳過 DB 查詢

**改動範圍**：加 `responseSchema` + 加驗證 / 重試分支。比階段 1 大但仍可控。

### 階段 3 — 把該告訴模型的事補上（上下文注入）

**目標**：很多錯誤是「系統知道、卻沒告訴模型」。

- **當前 context 要傳下去**（畫面範圍、檢視對象、時間週期、使用者角色）
- **規則要嚴**：只有**問題完全沒提到相關維度時**才套用當前 context
  - 否則「全台這週賣幾台」會被硬加門市過濾，變成另一種錯
- **單一 schema 定義**：consumer 跟 model 不要各自手抄一份

### 階段 4 — 脈絡衛生（防污染）

**目標**：防「多輪對話脈絡污染」。

- **查詢結果不留對話歷史**：當輪注入、用完即丟
- **切換 context 時，畫面與模型記憶要一致**：要嘛把 history 帶進新 session、要嘛連畫面一起清
- **三種記憶一致**：畫面訊息、SQL 生成器可讀的 history、回答模型的 session—— 三者不能各說各話

## 防腐化 pattern：Schema 要是「活的」不能是「死的」

### 核心洞察

**死 schema**（手抄的字串）：
- 漏了什麼不會發生
- 不崩潰、不報錯
- 只在有人問到時默默給錯答案
- **沒有回饋迴路 → 必然腐化**

**活 schema**（app 畫面會壞給你看）：
- 寫錯或漏欄位，畫面馬上壞
- 強制維護

**解法**：讓 LLM 的 schema **搭上 app 的回饋迴路**——共用單一 schema 定義：

```
constants/schema.ts (單一真相源)
    ├─→ app 從它導出 COLUMN_MAP（畫面壞 = 告警）
    └─→ LLM 從它生成 schema 說明文字
```

**注意期望值**：
- 這是**不對等共用**——共用定義是 LLM 的需求規格，app 只吃其中一小塊（欄位名對照）
- **它取代不了現有 prompt**——型別處理、單位換算、禁 JOIN、few-shot 範例都是手寫的知識
- 共用只讓欄位清單那段改為自動生成，prompt 約縮短三成

### 最陰險的坑：單位錯誤（0~1 比率 vs 百分數）

- 欄位 `ip_to_o_pct` = 0.7058 實際是 70.6%
- 模型直接回答「0.71%」—— **錯兩個數量級、不報錯、不拒答、看起來完全合理**
- 所有失效模式中**最難察覺**的一種

**對策**：schema 定義**必須含單位語意**（不只欄位名 + 型別）。

## 設計決策：拒絕哪些誘惑

### ❌ 換大模型

- 理由：上線成本、延遲、cost 考量
- 若維持弱模型 → 本 methodology 四階段全部適用
- 若升級大模型 → 階段 2、3 的程式驗證**仍然要留**（大模型照樣會偶發）

### ❌ 改用 function calling

- 弱模型的 tool use 可靠度比一般生成**更差**
- 等於把最關鍵的決策交給最不可靠的能力
- 「這題不用查」由 `needsQuery: false` 解決
- 「回答模型不核對 SQL」由程式驗證解決——比模型自律可靠

### ❌ 「叫模型不確定時反問」當主力

- 對已證實錯誤無效（模型不覺得自己錯）
- 反效果（鬆調會過度反問）
- 保留反問機制，但由程式觸發

### ❌ 「自檢在同一條 prompt 裡做」

- 弱模型會把檢查清單吐出來污染輸出
- 自檢改用階段 2 的 structured output + 外部程式驗證

---

## 做這件事的天花板

**程式驗證只能抓「條件有沒有出現在 SQL 裡」，抓不到「條件用錯了」**：
- 例：模型把 `A 店` 塞進 `section` 欄而不是 `store_name` 欄
- 字串檢查會通過
- 要再往上就得驗證 SQL 語意，成本高很多

**知道這個缺口存在，不假裝沒有**。

---

## 可見性：永遠讓產出的 SQL 看得到

**鐵則**：產出的 SQL / function call 要在**使用者介面**折疊顯示。

- 否則「數字怪怪的」只能反推
- 加這個是小改動，但對 debug 效率是 10x

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 相信弱模型會自覺舉手 | 錯誤 SQL 跑過、數字回來、模型不反問 | 程式驗證 + 強制 structured output |
| 把反問當主力 | 要嘛漏抓、要嘛過度反問 | 反問改由程式觸發 |
| 一堆 systemInstruction 擋幻覺 | 擋得了無中生有，擋不了答非所問 | 加「核對條件」的守門規則 |
| 死 schema 手抄兩份 | 必然腐化、不會告警 | 單一定義、共用給 app |
| 欄位只寫名字沒寫單位 | 0.71% vs 70.6% 看不出來 | schema 必須含單位語意 |
| 自檢塞進同一條 prompt | 檢查清單污染輸出 | structured output + 外部驗證 |
| 查詢結果留對話歷史 | 多輪後模型抓錯數字 | 當輪注入、用完即丟 |
| 切換 context 不清記憶 | 畫面、SQL 生成器、回答模型各說各話 | 三種記憶強制一致 |
| 當前 context 不注入 | 「這週賣幾台」答全公司 | 傳 scope / entity 進去 |
| context 套太鬆 | 「全台」被硬加門市過濾 | 只有問題沒提維度時才套 |
| SQL 不可見 | debug 只能反推 | 折疊顯示 |
| 換大模型想一次解 | cost + 延遲上升，問題還會偶發 | 階段 2 驗證不管什麼模型都要留 |

## 檢核清單（弱模型管線 review 前對一次）

- [ ] 階段 1：有 few-shot 樣板嗎？軟建議是否改硬規則？
- [ ] 階段 2：回 structured output 嗎？程式端逐條驗證 condition 嗎？
- [ ] 階段 2：缺條件會自動重試一次嗎？
- [ ] 階段 2：有 `needsQuery: false` 的 escape hatch 嗎？
- [ ] 階段 3：當前 context（scope、entity）傳進去了嗎？套用規則夠嚴嗎？
- [ ] 階段 4：查詢結果不留 history 嗎？切換 context 三種記憶一致嗎？
- [ ] Schema：有單一定義檔嗎？含單位語意嗎？
- [ ] SQL 可見性：使用者介面能看到產出的 SQL 嗎？
- [ ] 知道程式驗證的天花板（條件用錯欄位抓不到）嗎？

## 一句話總結

> **弱模型不是問題，弱模型 + 無驗證才是**。讓它說自己讀到什麼、程式確定性驗證、錯了重試一次、重試還錯才反問——這四步比換大模型便宜、比自檢可靠。
