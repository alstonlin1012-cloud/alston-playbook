# 判準演化追蹤 methodology

> 判準框架不是一次寫對的——是**用錯了、被推翻、再修正**來的。這份 methodology 處理「舊報告 + skill commit 歷史 + 現行判準」三者的關係：舊報告是**修正前的樣子**，留著當對照，不是為了情懷，是為了「為什麼要有這條規則」有據可查。

## 情境（什麼時候拿出來用）

- 做過一個案子，然後把方法論抽成 skill / framework / playbook
- 判準寫到第二版、第三版，推翻過前版
- 新案子拿舊報告當範本時，踩到前版錯誤的坑
- 想把舊報告刪掉但覺得可惜
- 要跟同事解釋「為什麼現行判準這條這麼嚴」

**跟 [[verifiable-judgment-framework-writing]] 的差別**：
- 那份講**怎麼寫判準**（meta rule）
- 這份講**判準怎麼演化、怎麼記錄演化**

## 核心主張

**判準的每一條規則都對應一次真實的修正**：
- 刪掉舊報告 → 規則變成沒來由的教條
- 留著舊報告 + 標明「這是前版，已被現行判準推翻」→ 規則有血肉
- 新案子照抄舊報告 → 重複前版錯誤（災難）

**三件事要一起留**：
1. **現行判準**（single source of truth）
2. **舊報告 + 偏差對照表**（為什麼要有這條規則）
3. **「正確範本」**（用現行判準重跑、通過 3 個 agent 收斂的）

## 骨架（NOTE 檔的六節）

每個有「演化」的 skill / framework 旁邊放一份 `NOTE-報告版本與判準演化.md`：

### § 1. 讀這些報告之前先看這份（前言）

**鐵則**：第一節就要警告。

```markdown
# ⚠️ 讀這些報告之前先看這份

這個資料夾裡的報告是 `<skill 名>` 的**前身，不是它的範本**。

它們寫於判準還在演化的過程中，**其中幾個核心結論後來被推翻了**。
直接照抄會複製 skill 現在明文禁止的錯誤。

**正確的範本是 `TEMPLATE-<案名>-現行判準版.md`**——
同一個案子、同一份資料，用現行判準重跑，N 個獨立 agent 判定完全收斂。

現行判準本身見 `<skill_path>/references/<framework>.md`。
```

**為什麼**：讀報告的人不會先讀 README。警告放第一行才擋得住。

### § 2. 最重要的一件事（最大的那條修正）

**鐵則**：把**最容易踩的那條**放最前面，三段式：

```markdown
## 最重要的一件事：<判準名>

**當時的寫法**：<舊版判斷方式>
→ <舊版結論>

**現行判準**：<新版判斷方式>
→ <新版結論>

**這是框架初版判錯、後來修正的第一個地方，也是 skill 的第一條紅旗。**
```

**要點**：
- 新舊結論要寫明顯「相反」（不是「微調」）
- 標「第一條紅旗」= 讀的人知道「如果只記一件事，記這個」

### § 3. 各份報告的定位表（index）

每份舊報告列：性質 / 對現行判準的偏差：

```markdown
| 檔案 | 性質 | 對現行判準的偏差 |
|------|------|-----------------|
| `report_v1.md` | 基礎版 | 判準尚未成形 |
| `report_v2.md` | 改版 | **偏差最大**：<具體錯在哪> |
| `report_present.md` | 會報版 | 講法最接近現行判準，但 <還保留什麼問題> |
| `thematic_A.md` | 專題 | 結論方向對，但**歸因寫進了主結論**（判準後來禁止） |
| `integrated.md` | 整合版 | 混合：有對的有錯的 |
| `skill-draft.md` | skill 原始草案 | 已演化成現在的 skill，保留作起點對照 |
| **`TEMPLATE-現行判準版.md`** | **★ 正式範本** | **無偏差——要照著做的那一份** |
```

**關鍵**：**用 ★ 符號標「正式範本」那一份**。其他都是歷史。

### § 4. 被推翻或收緊的結論（列舉）

**三類最常見的演化**：

#### 4.1 「範圍錯放」—— 拿標的代表整體

舉例：「拿接手的那家店表現代表整個接手方」
- 正確：看整個經營者的版圖 × 效率
- **「標的守成」與「接手方贏了」可以同時成立**

#### 4.2 「因果超過證據」—— 把事實當因果

舉例：虹吸要拆**三層**：

| 層 | 本案 | 是否可說 |
|----|------|---------|
| ① 同區虹吸 | 可證（直營在該區據點 0、量 0） | **可以說「沒有」** |
| ② 跨區**流向** | 有買方地理就可算 | **必須陳述** |
| ③ 跨區虹吸的**因果**（「這些客本來會在標的成交」）| 恆為待驗假設 | **即使有買方地理也證不出來** |

舊分析把 ② 的事實直接當 ③ 的因果——**跨越了證據能支撐的範圍**。

#### 4.3 「否定命題也要證據」

舊版可以寫「不是 X」。現行判準要求：**否定式結論同樣需要證據**。

### § 5. 這批報告最有價值的一份（意外之財）

**鐵則**：舊報告裡**某份是唯一用某稀有資料做的分析**——標明它。

```markdown
`<某份>.md` 是唯一使用<稀有資料>的分析。

它算出了 skill 的模組 X 現在只能寫在紙上的東西——
<具體發現>。

**skill 的模組 X 規則就是從這份分析歸納的。**
規則寫成後有很長一段時間沒被驗證過——10 個測試案例沒有一個有<稀有資料>。

**用現行判準重跑時，模組 X 才第一次被實際執行**，並立刻帶回兩條修正：
- <修正 1>
- <修正 2>

**規則從紙面到執行之間，確實會漏東西。**
```

**為什麼要寫**：
- 證明「現行判準不是閉門造車」
- 讓下一次演化有起點
- 下任新同事看得出「這份報告的稀有性」

### § 6. 為什麼留著這些報告

```markdown
## 為什麼留著這些報告

判準的每一條規則都對應一次真實的修正。
這批報告是**修正前的樣子**——它們和 skill 的 commit 歷史互為對照，
說明「為什麼要有這條規則」。

刪掉它們，規則會變成沒有來由的教條。
留著，但要知道它們是起點不是終點。
```

## 搭配：skill / framework 本身要做什麼

NOTE 檔只是一半，另一半在 skill / framework：

- **每條規則標起源**：「本條規則來自 <案名> 的 <某份報告> 的修正」
- **commit message 寫清楚**：「<判準 X> 從 'can' 收緊為 'must'，因為 <案名> 踩到」
- **測試案例列表**：記錄哪些案例曾用過哪個版本的判準

這讓 commit history + NOTE 檔 + skill 現狀 三者互為註腳。

---

## 「規則從紙面到執行之間會漏東西」

**鐵則**：判準不被實際跑過，就不是成熟判準。

**典型漏洞**：
- 欄位名沒驗證（例：某欄位只有特定 segment 有值，當分母會算出 100% 假結果）
- 分層沒拆細（例：虹吸 ②/③ 要分，舊版合在一起）
- 否定命題的證據門檻（例：「沒有 X」需要什麼才算證據）

**對策**：
- 現行判準至少要**用現實案子跑過一次**（不是只在白板推導）
- 跑過後**三個 agent 獨立判定收斂**才算驗證完成
- 跑過時發現的 bug → 立刻回填到判準

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 刪掉舊報告 | 規則變沒來由的教條 | 留著 + NOTE 標記 |
| 舊報告直接照抄 | 複製前版錯誤 | NOTE 第一行警告 + 指向正式範本 |
| 修了判準但沒更新 NOTE | 新案子踩到舊坑 | NOTE 跟 skill 一起改 |
| 判準沒跑過現實案子 | 從紙面到執行會漏 | 至少 1 案 + 3 agent 收斂 |
| 偏差描述太抽象 | 「有些問題」 | 具體寫「偏差最大：拿 X 代表 Y」 |
| 沒標「正式範本」 | 下任分不清要照哪份 | ★ 符號標出來 |
| commit message 只寫 「update」 | 演化軌跡丟失 | 「X 從 can 收緊為 must，因為 <案>」 |
| 收緊後不回頭看舊案 | 錯誤分析散在各處 | 收緊時列出受影響的舊案 |
| 否定命題不要求證據 | 「不是 X」沒憑據 | 否定式也要 evidence |
| 事實直接當因果 | 跨越證據能支撐的範圍 | 拆三層：可證 / 可陳述 / 待驗假設 |
