# 報表維運 SOP 骨架

> 報表壞掉時（收到告警、數字對不上、資料沒更新）**不需要問人**，照對應 SOP 就能定位問題並修復。這份是 SOP 的**骨架規範**——每份報表照同一套章節寫，新人、agent、半夜被叫起來的 oncall 都能照做。

## 情境（什麼時候拿出來用）

- BI team / 資料團隊有幾份「關鍵報表」（管理層、通路、主管機關每天看）
- 報表壞一次就有人被 call
- 原作者離職或請假時沒人會修
- 當前做法是「問 LINE 問群組」→ 不穩、無法複製、下次還會壞
- 想把「口傳知識」沉澱成 asset

**跟 [[data-flow-playbook-skeleton]] 的差別**：那份是**設計**（怎麼建資料流，F1-F4 血緣），這份是**維運**（壞了怎麼修，三步定位）。

## 核心主張

**維運 SOP 不是文件，是「可直接複製的指令集 + 固定章節格式」**：

1. **使用流程三步**：找到報表 → 定位問題 → 執行修復
2. **兩條鐵則**：
   - 鐵則 1：**上游先修、再修下游**
   - 鐵則 2：**重跑時每一步等上一步完成再做**
3. **固定章節**：每份 SOP 同一套章節格式，不自由發揮
4. **指令可直接操作**：寫清楚在哪台主機、跑哪個檔案、哪個排程
5. **只放修復用的資訊**：欄位定義、完整 lineage 放別處，SOP 不重複

## 使用流程（三步定位 + 一步驗證）

```
① 找到報表 ──► 從 README 索引打開對應 SOP
       │
       ▼
② 定位問題 ──► 看 §4「快速故障排除」，依症狀找是哪支資料源壞
       │
       ▼
③ 執行修復
   │
   ├─ 精準修一支   ──► §6「資料源修復步驟」照指令操作
   │
   └─ 多支異常 / 懶判斷 ──► §5「全鏈無腦重跑」從上到下全部重跑
       │
       ▼
④ 確認完成 ──► 回報表系統驗證資料源都已重新擷取
```

**「無腦重跑」是 feature 不是 bug**：半夜 oncall 能照流程走比省時間重要。

## 固定章節（每份報表 SOP 必備）

| 章節 | 內容 | 一句話用途 |
|------|------|-----------|
| §1 報表基本資訊 | 名稱、workbook、負責人、訂閱者、更新頻率、監控告警 | 「這是什麼報表」 |
| §2 報表結構 | 由哪幾支資料源組成、join 邏輯 | 「這報表怎麼拼起來」 |
| §3 資料源依賴地圖 | 上游 → 下游流向圖（mermaid） | 「資料從哪來到哪去」 |
| §4 快速故障排除 | 症狀 → 問題點 → 先做什麼 | **排錯起點（最常翻）** |
| §5 全鏈無腦重跑 | 照順序重跑整條鏈 | 「多支壞 or 懶判斷時用」 |
| §6 資料源修復步驟 | 每支資料源的執行檔／排程／除錯步驟（依上游 → 下游排序） | 「精準修一支時用」 |
| §7 常用 SQL / 檢核工具 | 可直接複製的檢核 SQL | 「驗證資料對不對」 |
| 附錄 | 主機環境、代碼對照、聯絡窗口 | 「速查卡」 |

### § 4 的寫法（最常翻、最容易寫爛）

**症狀 → 問題點 → 先做什麼** 表格：

| 症狀 | 問題點 | 先做什麼 |
|------|--------|---------|
| 報表數字沒更新 | 可能是 feeder A / B / C | 跑 `rs_daily_order_check` 看哪支沒更新 |
| 數字看起來少 | 可能某 join 掉資料 | §7 的對帳 SQL 跑一次 |
| 時間戳落後 | 上游 ETL 卡住 | §6 的 feeder A 重跑 |
| 整個空白 | 資料源連不上 | 先驗主機 `10.X.X.X` 狀態 |

**設計要點**：
- 症狀用 **使用者語氣原話**（「數字沒更新」比「latency」好）
- 「先做什麼」給具體動作，不是「檢查資料」
- 每個症狀都有對應 §5 / §6 / §7 的跳點

### § 6 的寫法（給精準修的人）

每支資料源一個子章節：

```markdown
### 6.X <資料源名稱>

- **上游**：<從哪支接來>
- **執行點**：`<主機>` 的 `<絕對路徑>`
- **排程**：Airflow DAG `<dag_id>` / 每日 XX:XX
- **手動重跑指令**：
    ```
    <可直接 copy-paste 的指令>
    ```
- **常見錯誤 → 處理**：
  - error A → 做 X
  - error B → 做 Y
- **驗證成功**：資料源 timestamp 推進到今天
```

## 撰寫原則（五條）

### 原則 1 — 指令可直接操作
- 寫「在 `10.5.31.170` 的 `D:\BI_ETL\04_Program\Regular\XXX.tfl`」
- **不**寫「跑 XXX 的 prep」

### 原則 2 — 能放 link 就放 link
- Tableau 資料源、報表站台、參考文件一律附連結
- 讀的人不用自己 google

### 原則 3 — 只放修復用的資訊
- 欄位定義、完整 lineage → 放中央 Data SOP
- SOP 只放「怎麼修」，不重複寫知識

**為什麼**：資訊重複 = 兩處變更不同步 = 新人踩雷。中央有單一真相來源，SOP 連過去。

### 原則 4 — 未知處標 `🔧 待補`
- 不確定的內容先佔位
- 比「假裝沒這段」好：讀的人知道「這塊要去問 owner」

### 原則 5 — 符合固定章節
- 不自由發揮
- 看這份就能寫下一份

## 新增一份 SOP 的流程

1. **複製空白範本** `templates/report-sop-template.md` → `reports/<報表名>.md`
2. **逐節填寫**（不確定的留 `🔧 待補`）
3. **對照驗收 checklist** 逐項確認（見下方「檢核清單」）
4. **回 README 的報表索引** 更新自己那一列的連結與狀態
5. **請一位同事試跑 §5**（找人照 SOP 跑一次，看哪段不夠清楚）

## 共用速查（README 附錄）

寫在 README 底部，所有 SOP 共用：

- **主機清單**：哪台跑 ETL、哪台跑 Python、哪台連 DB
- **常用連結**：報表站台、中央 Data SOP、對帳工具
- **Log 位置**：出錯時 log 落在哪台哪個路徑

**為什麼要共用**：每份 SOP 都重複寫一遍 → 主機 IP 變了十份都要改。

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| SOP 寫成「設計文件」 | 細節講一堆、怎麼修看不懂 | 只放修復用資訊 |
| 症狀用技術詞 | 使用者告警看不懂對應哪段 | 用使用者原話寫症狀 |
| 「檢查 X」當動作 | 讀的人不知道要怎麼檢查 | 動作 = 具體指令 |
| 所有 SOP 自由發揮 | 每份章節格式都不一樣 | 固定章節、硬性要求 |
| 欄位定義寫進 SOP | 兩處變更不同步 | 連去中央 Data SOP |
| 沒 § 4 跳點 | 鎖定不到問題點 | 症狀 → 問題點 → 動作表格 |
| 沒試跑 | 寫得很美但新人跑不動 | 找同事試跑 § 5 |
| 下游先修 | 修完一下又壞 | 鐵則 1：上游先修 |
| 一次重跑多層 | 第一層還沒好第二層已經失敗 | 鐵則 2：每步等上一步 |
| `🔧 待補` 留太久 | 變石化文物 | 設 review 週期 |

## 檢核清單（新 SOP 驗收前對一次）

- [ ] §1-§7 + 附錄全部有嗎？
- [ ] §1 有名稱、workbook、負責人、訂閱、更新頻率、監控告警嗎？
- [ ] §3 有 mermaid 依賴圖嗎？
- [ ] §4 的症狀用使用者原話寫嗎？每個症狀有跳點嗎？
- [ ] §5 全鏈重跑的順序正確（上游 → 下游）嗎？
- [ ] §6 的每個子章節有：上游、執行點、排程、手動指令、常見錯誤、驗證成功？
- [ ] §7 的 SQL 可以直接 copy-paste 跑嗎？
- [ ] 指令寫到「哪台主機 + 哪個絕對路徑」嗎？
- [ ] 連結都放了嗎（報表站台、Data SOP、對帳工具）？
- [ ] 不確定的地方標 `🔧 待補` 了嗎？
- [ ] 找一位同事試跑一次 §5 看哪段不夠清楚了嗎？
