# 紅綠燈設計 pattern

> 紅綠燈（🟢🟡🔴）看起來簡單，實際藏很多決策：門檻怎麼訂、帶寬多少、空白怎麼留、燈號跟數字怎麼擺、同一套規則多個對象如何複用。這份文件給一組可直接套的設計 pattern。

## 情境（什麼時候拿出來用）

- 要設計管理 dashboard 的「這家店／這個人健不健康」指標
- 要把幾十個指標壓成一眼可讀的 overview
- 要讓非資料背景的老闆也能一秒看懂
- 要做跨期／跨區可比的健檢
- 想避免「全紅」或「全綠」的失效狀態

## 核心主張

1. **相對同儕 ± 帶寬，不是絕對門檻**
2. **燈號 + 絕對量並列**（燈號是相對、絕對量是達標）
3. **先燈號、再佐證**（版面順序）
4. **細節純呈現、不上燈**（太多燈會失去訊號）
5. **空白／留白是訊號**，不是遺漏
6. **規則寫進產出檔本身**（程式／文件同源）

---

## 骨架一：燈號判準（相對同儕 ± 帶寬）

```
燈號條件（帶寬 ± X pp）：
🟢 單位 > 同儕基準 + X pp
🟡 同儕基準 − X pp ≤ 單位 ≤ 同儕基準 + X pp
🔴 單位 < 同儕基準 − X pp
空白：見下 §留白通則
```

**同儕基準怎麼算**：
- **達成率／成長率**：同期區域加總（Σ分子 / Σ分母），不是平均
- **效率率（IP>O% 等）**：同期區域加總
- **結構比例**（如獎金佔收入）：同期區域中位數

**為什麼用加總而不是平均**：
- 平均會被小基數離群值拖動
- 加總反映「如果我把這群看成一整個的話，我的真實指標」

### 帶寬選擇

| 帶寬 | 適用 | 代價 |
|------|------|------|
| ± 3pp | 嚴格、燈變化頻繁 | 容易全紅或全綠 |
| ± 5pp | 預設 | 平衡 |
| ± 10pp | 寬鬆、燈較穩 | 訊號弱 |

**鐵則**：帶寬寫在 config 常數，不在腳本裡 hard-code。

---

## 骨架二：燈號 ≠ 達標（命門）

**最常見誤解**：綠燈 = 達標。

**真相**：綠燈只代表**相對優於同儕平均**，不代表**絕對達標**。

**典型反例**：
- 整區平均達成率 56%，某店做 69% → 🟢（優於同儕 13pp）
- 但 69% 絕對值仍不達標（通常要 ≥90%）

**校正**：
- **燈號 + 絕對量並列**（燈號說相對位置，絕對量說達標程度）
- 整區衰退時全部會落在黃燈 → 判讀時必須同時看絕對量
- 燈號訂位「相對優劣」，絕對量訂位「過關沒過關」，兩者缺一不可

## 骨架三：先燈號後佐證（版面順序）

典型版面（由上到下）：

```
Row 1-5   燈號區（🟢🟡🔴）              ← 一眼看
Row 6-10  診斷結論（人工／AI 注入）       ← 燈號的解釋
Row 11-30 明細指標（數字版）              ← 佐證
Row 31-40 區域 benchmark（同儕基準）      ← 比什麼
Row 41-50 TPO 漏斗（純呈現、不上燈）      ← 問題在哪一層
Row 51+   獎金 / 體檢 / 補充資料          ← 配合判讀
```

**原則**：
- 燈號區**最上**（一眼可讀）
- 診斷結論**緊接**（燈號的語義）
- 數字區在下（翻下去看細節）
- 燈號公式**只做比較、不重算**（數字區已算好）

## 骨架四：對象集合三道篩選

要上紅綠燈的「對象集合」常需要三道篩選：

| 道 | 條件 | 典型 |
|----|------|------|
| 1 | 屬於目標範圍 **且** 全期有目標（`target > 0`） | 排除 AS／HQ／加盟／已閉店 |
| 2 | 以**名稱**合併（不用 ID） | 處理換代碼的門市 |
| 3 | 首月與末月**皆有實際列** | 擋期內收店與新開 |

**為什麼用名稱合併不用 ID**：資料系統換代碼時，同一家店會出現兩個 ID、過渡期並存。拆成兩欄會讓同一實體的走勢各斷一截。

**鐵則**：篩選條件寫在 `Data.__init__`，不另外維護排除清單。排除清單會跟程式脫鉤。

---

## 骨架五：細節純呈現，不上燈

**命門**：燈號太多 = 失去訊號。

**作法**：把指標分兩類：
- **判讀類**（達成率、成長率、關鍵效率） → **上燈**
- **診斷類**（TPO 三轉換率、客群結構、產品結構） → **純呈現、不上燈**

**原因**：
- 判讀類是**管理層要盯的**（上燈才會看）
- 診斷類是**解釋原因用的**（看細節才有用）
- 全部上燈 = 一片紅綠黃、什麼都重要 = 什麼都不重要

## 骨架六：留白（空白）通則

空白格不是 bug，是明確訊號：

| 樣態 | 意義 | 處理 |
|------|------|------|
| ① 該期不存在 | 當時該人／店還沒進職位 / 開業 | 整欄留白 |
| ② 當期無資料 | 系統異常或資料未到 | 當格留白 + 註記 |
| ③ 單位當期數字極少 | 分母過小不下判定 | 當格留白 + 註記樣本數 |
| ④ 跨 ID 過渡 | 新舊 ID 換期中 | 整期留白，避免誤判 |
| ⑤ 整群體無發放／無活動 | 當期無基準可比 | 當列全留白，不評分 |

**原則**：
- 留白要有**明文定義**（寫在規則說明分頁）
- 不同樣態的留白用**不同視覺**（例：灰色 / 斜線 / 空字）
- 「沒給燈 ≠ 漏做」

## 骨架七：規則寫進產出檔本身

產出的 xlsx 要有**「規則說明」分頁**，寫清楚：

```markdown
## 規則說明

### §1 判準
- 🟢 單位 > 區域基準 + 5pp
- 🟡 ± 5pp
- 🔴 單位 < 區域基準 − 5pp

### §2 同儕基準定義
...

### §3 門市集合（本期 N 家）
- 三道篩選的詳情
- 被擋的名單

### §4 留白通則
- 五種樣態

### §5 資料來源
...

### §6 本期參數
- BO 月份、BO 週數
- 25Q4 基期
```

**原則**：
- 規則與產出 xlsx 同一個檔（不要分開存 md 與 xlsx）
- 分頁說明要跟程式**同源**（例：由程式 `RULES_STORE` 常數自動寫進分頁）
- 改規則 = 同時改程式 + 文件 + 說明分頁

## 骨架八：驗算三件（產出前跑）

```python
# verify_values.py
# 獨立重算一份（不 import 產出常數）

def test_light_count():
    """每列燈號數 = 有效門市數"""
    ...

def test_benchmark_consistency():
    """benchmark 列 = Σ分子/Σ分母（不是 AVG）"""
    ...

def test_blank_rules():
    """空白格的數量 = 預期留白數"""
    ...
```

**原則**：每期跑新資料前，驗算必過才產出。

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 絕對門檻判達標 | 整區衰退時全紅 | 相對同儕 ± 帶寬 |
| 綠燈 = 達標 | 老闆以為沒事 | 燈號 + 絕對量並列 |
| 全部指標上燈 | 一片顏色、訊號弱 | 判讀上燈、診斷純呈現 |
| 空白當 bug | 一直問「為什麼沒資料」 | 留白明文定義 + 註記 |
| 用 ID 聚合 | 換代碼時斷裂 | 用名稱聚合 |
| 平均當基準 | 離群值拖動 | Σ分子/Σ分母 |
| 規則只在文件 | 程式與文件漂移 | 同源：規則分頁由程式產 |
| 帶寬 hard-code | 改規則要動多處 | 寫在 config 常數 |
| 不設篩選集合 | 新開 / 已閉店混進 | 三道篩選 |
| 燈號重算數字 | 公式複雜、對帳難 | 燈號只做比較，數字區先算好 |

## 真實案例骨架（去識別化）

### 案例 1：絕對門檻全紅
原本紅綠燈判達成率 ≥80% 綠、60-80% 黃、<60% 紅。某期全區平均 56%，全員紅。管理層看了麻木。
改用相對同儕 ± 5pp 後：69% 綠（優於區均 13pp）、56% 黃、45% 紅。**訊號可讀**。
**代價**：綠燈不等於達標 → 配絕對量並列解決。

### 案例 2：全部指標上燈的失效
某 dashboard 把 20 個指標都上燈，一頁 400 個燈號。管理層打開只看三個最亮的。
改為「判讀類 5 個上燈、診斷類 15 個純呈現」後，燈號密度降到可讀。

### 案例 3：換 DMS 代碼導致斷裂
某門市換 DMS 代碼，舊 ID 25P10-26P1 有量，新 ID 25P10-26P7 有量，過渡期兩 ID 並存。原本按 ID 聚合，看起來是兩家店各斷一截。
改用**名稱聚合**後，一家店完整連續。過渡期 traffic 記舊 ID、IP 記新 ID 的交界也被合併。

### 案例 4：規則文件漂移
程式用帶寬 5pp，文件寫 10pp。半年後有人照文件 review 結果，被業務打臉。
**校正**：規則說明分頁由程式常數 `BAND` 自動產生，改一處同步兩邊。
