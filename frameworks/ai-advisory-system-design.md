# AI 行動建議系統設計框架

> 業務部門常見痛點：裝了 AI 助手但產出都是「加強服務、提升業績」這種誰都能講的廢話。問題不在 LLM 不夠強，在系統設計。這份文件給一組硬約束，讓 AI 輸出**強制含數據＋對比＋可行動**，無法達到就**不要出**。

## 情境（什麼時候拿出來用）

- 要做內部 AI 助手／行動建議機器人
- 使用者反饋「AI 講的都是廢話」
- 要給門市主管／店長／業務具體行動指引
- 想避免 LLM 幻覺、通用話術、空泛建議
- 有上游會議紀錄／報告要轉成知識資產

## 核心主張

**寧可少建議、不可弱建議**。

當 AI 無法滿足說服力七要素（見下）→ **必須降級**為「資訊不足，請補充 X」，而非強行產出空泛話術。

---

## 骨架一：四階段架構（知識管道 + AI 服務）

```
[供應部門]                            [消費場景]
    │                                       ▲
    │ Stage 1                        Stage 4 │
    ▼ 紀錄供應介面                    AI API│
┌────────┐   ┌─────────┐   ┌────────────┐
│ 攝入層 │──►│Stage 2  │──►│ Stage 3    │
│        │   │知識資產 │   │ AI 服務    │
└────────┘   │轉化     │   │            │
             └─────────┘   └────────────┘
                   └───── 我們擁有全程 ─────┘
```

| Stage | 做什麼 | 擁有者 | 關鍵交付 |
|-------|-------|-------|---------|
| 1 紀錄供應 | 接收上游半結構化資料 | 上游部門 | metadata 完整 |
| 2 知識資產轉化 | 攝入 → 概念化 → 存辭典 | 本部門 | 概念辭典 + 案例庫 |
| 3 AI 服務 | prompt + 檢索 + 生成 | 本部門 | 符合七要素的輸出 |
| 4 交付介面 | API / UI | 下游 | 穩定 schema |

**鐵則**：
- 四 stage **分清擁有者**（避免跨部門責任模糊）
- 每 stage 有 SLA 與驗收指標
- Stage 3 的輸出受 Stage 2 的知識資產約束

## 骨架二：AI 輸出說服力七要素（北極星）

**定位**：這不是「我們產出什麼」，是「最終輸出必須達到的標準」。反向約束知識資產收什麼、prompt 怎麼設計。

| # | 要素 | 層級 | 必填欄位 | 降級行為 |
|---|------|------|---------|---------|
| 1 | **數據—洞察—行動三段式** | 強制 | `[數據]` `[洞察]` `[行動]` 缺一不可 | 任一段缺資料 → 不出建議，改「資訊缺口提示」 |
| 2 | **對比敘事** | 強制 | 數據附至少 1 個對比錨點 | 找不到對比 → 標記孤立數據、洞察降級 |
| 3 | **概念命名** | 強制檢索／選填創造 | 用既有辭典、不自創 | 無既有概念 → 標 `待命名候選` 進人工佇列 |
| 4 | **可追溯來源** | 強制 | 每條建議指向來源紀錄 ID | 無來源 → 不出 |
| 5 | **情境適配** | 強制 | 匹配店型／階段／狀態 | 沒 fit → 標「情境不明」 |
| 6 | **4W1V 行動結構** | 強制 | Who / What / When / Why / Verify | 任一缺 → 不出 |
| 7 | **時效性** | 強制 | 標「資料截止日 vs 時效限制」 | 過期 → 不出 |

**鐵則**：**寧可少建議、不可弱建議**。七要素任一不過 → 降級，不空話。

---

## 骨架三：三段式輸出格式

每條建議強制含三段：

```
[數據錨點]
"W17 IP 轉化率 84%（W14 起逐週上升）"
← 至少 1 個具名指標：名稱 + 數值 + 時間範圍

[洞察]
"這間店的轉化率改善來自 X 策略，是全區唯一突破的店"
← 1-3 句：為什麼這數據重要、指向什麼問題／機會

[行動]
Who: 區經理
What: 複製 X 策略到同區 S2 群其他店
When: W18 前
Why: 連動 IP 轉化率提升、全區可增 N 台
Verify: W21 時 S2 群平均 IP% 應 ≥ Y
```

**鐵則**：三段缺一就**降級**，不產空話。

## 骨架四：對比敘事規範

**反模式**：「永和區車退 22 張，需加強」—— 沒對比、沒 benchmark、沒洞察。

**正模式**：「永和區車退 43 → 22（-48.8%），**優於全區平均 -12%**，**接近健康水準 ≤20 的門檻**」

**對比錨點類型**：
- (a) 自身時間序列（上週／上月／同期）
- (b) 同類型店／同區域
- (c) 標竿值（區域平均、健康水平、目標值）

**變動表達**：
- 必含「**絕對變動 + 相對變動**」
- 例：`43 → 22（-48.8%）` 不是 `-48.8%`

**找不到對比的處理**：
- 標記為 `孤立數據`
- 洞察強度自動降一級
- 提示「建議補充對比基準」
- **不要**為了講故事瞎掰對比

## 骨架五：概念辭典（禁止 AI 自創）

**為什麼**：
- LLM 自創概念 = 每次說法都不同、使用者困惑
- 概念是跨期跨店的歸納，需要人工審核
- 概念命名錯誤成本高（之後報告會引用）

**規範**：

| 規則 | 說明 |
|------|------|
| 檢索優先 | 描述歸納性現象時，**必須優先檢索概念辭典**並使用既有命名 |
| 禁止自創上線 | 辭典中無適用概念時，**禁止 AI 自行命名上線** |
| 候選佇列 | 可標記為 `待命名候選` 進入人工審核 |
| 觸發條件 | 跨期、跨店、跨指標的歸納性洞察 |

**辭典的架構**：
```yaml
# concept_dictionary/
- id: environmental_sensitivity
  name: 環境敏感度
  definition: 門市業績受外部客流（天氣、檔期）影響程度
  trigger_pattern: 業績波動與客流波動高度相關、本體操作無明顯變動
  examples:
    - [case 1 id]
    - [case 2 id]
```

**作用**：
- AI 檢索 → 找到概念 → 用既定命名
- 新現象 → 標候選 → 人工審核後納入辭典

## 骨架六：利害關係人地圖

每個角色寫一行，避免跨部門責任模糊：

| 角色 | 對我們的角色 | 關鍵期待 | 我們的承諾 |
|------|-------------|---------|----------|
| 供應部門 | 上游資料供應 | 低交付成本、不要求重寫格式 | 接受半結構化、提供 metadata 模板 |
| 消費場景 | 下游 API 消費 | 穩定 schema、可解釋輸出 | 多版型 API、契約穩定 |
| PM/顧問（curation） | 內部品質把關 | 工作量可控（≤ N hr/週） | 自動化萃取 + 候選佇列 |
| 基層使用者（信號主源） | 反饋主信號源 | 評分介面輕量 | 抽樣評分、不強制每條都看 |
| 最終使用者 | 反饋次信號源 | 採納／拒絕一鍵化 | 內嵌於 APP 介面（消費場景負責） |
| 本部門 | 知識管道營運 | 端到端可控、可優化 | 四 stage SLA、版本可追溯 |

## 骨架七：三層指標

| 層級 | 指標 | 目標值範例 |
|------|------|----------|
| **上游：紀錄品質** | 交付準時率 | ≥ 95% |
| | metadata 完整率 | ≥ 90% |
| | 萃取成功率（無需人工補件） | ≥ 80% |
| **下游：建議品質** | 反饋品質評分 | 平均 ≥ 4.0 / 5 |
| | 採納率 | ≥ 60% |
| | 採納後執行率 | ≥ 70% |
| | 業績連動（採納 vs 未採納指標差） | ≥ +5% |
| **自身：營運效率** | Curation 人力成本 | ≤ N hr / 週 / 人 |
| | 知識資產增長 | 概念 +N / 月 |
| | 退化警告 | ≤ 1 次 / 季 |

**鐵則**：三層不混，上游不好 ≠ 下游不好；自身效率不代表建議品質。

## 常見陷阱

| 陷阱 | 症狀 | 校正 |
|------|------|------|
| 允許空泛話術 | 「加強服務、提升業績」 | 七要素強制 + 降級規則 |
| LLM 自創概念 | 每次命名不同 | 概念辭典 + 候選佇列 |
| 孤立數據當建議 | 無對比的「22 張」 | 對比敘事強制 |
| 行動模糊 | 「加強追蹤」 | 4W1V 強制 |
| 看不到來源 | 無法追溯 | 建議 → 紀錄 ID |
| 四 stage 擁有者混 | 責任模糊 | 利害關係人地圖 |
| 只看下游指標 | 上游品質跟不上 | 三層指標 |
| 情境不匹配 | 給大店的建議推給小店 | 情境標籤必填 |
| 把寫作當 AI 核心能力 | 空話多、數字少 | 翻譯 vs 寫作分層（見 [[nl-to-sql-agent-layering]]） |

## 檢核清單（AI 輸出前自檢）

每條建議通過才出：

- [ ] 有數據錨點（名稱 + 數值 + 時間範圍）？
- [ ] 有洞察段（說明為什麼重要）？
- [ ] 有行動段（4W1V 完整）？
- [ ] 有對比錨點（絕對 + 相對變動）？
- [ ] 概念用的是辭典既有？
- [ ] 有來源紀錄 ID？
- [ ] 情境標籤匹配？
- [ ] 時效標籤有？
- [ ] 任何一項不過 → 降級為「資訊缺口提示」？

## 真實應用骨架（去識別化）

### 應用 1：門市營運行動建議
- Stage 1：區經理每週會議紀錄上傳
- Stage 2：萃取「行動 + 條件 + 效果」三元組
- Stage 3：店長打開 APP 看到建議，4W1V + 對比 + 概念
- Stage 4：採納／拒絕打分、信號回 Stage 2

### 應用 2：業績診斷解讀
- Stage 1：BI dashboard 自動產生週報
- Stage 2：萃取異常訊號
- Stage 3：AI 產生「這週 X 掉是因為 Y，建議 Z」
- Stage 4：區經理看、評分
- 若某週無足夠資料 → **降級為「本週訊號不足，無法產生建議」**而非瞎掰

### 應用 3：客訴／客服 AI 補充意見
- Stage 1：客訴紀錄
- Stage 2：歸類到概念辭典（「流程缺失」「訓練不足」「系統 bug」…）
- Stage 3：AI 給店長「這類客訴近期 N 次，建議 ...」
- Stage 4：店長採納後追蹤改善

**關鍵**：每個應用都用同一套七要素，不產空話。
